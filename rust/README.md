## Current implementation

- `runalith-domain`: typed workflow/task states, immutable-plan DAG validation, content hashes, evidence lineage, ten built-in role contracts, strict custom-role/custom-workflow contracts, typed input/output validation and deterministic immutable workflow-plan compilation. Custom compiler canonical bytes/hash match a Node-generated `previewCustomWorkflow` fixture.
- `runalith-artifacts`: private append-only SHA-256 content-addressed artifact storage with verified reads.
- `runalith-agg`: strict schema-v1 graph boundary with Node-compatible canonical graph hashing, metric provenance and conditional recovery contracts; bounded deterministic nominal search, unknown-aware path ranking, review-only Plan Graph projection, plus Node-compatible Phase 2 discriminator model v2 validation, feature extraction and logistic score. Estimates remain `model_estimate_unverified` and are not yet integrated into Phase 2 search. It never verifies claims or authorizes execution.
- `runalith-execution`: read-only Execution Graph projection over exact durable workflow/task/attempt/lease/result/provider-intent state. It does not execute commands or dispatch providers.
- `runalith-providers`: provider adapter contract plus GitHub Actions dispatch/reconciliation logic. Opt-in HTTP transport uses a bounded curl executor and host-supplied bearer token passed through stdin config, never argv. Runtime derives `inputs.runalith_intent_id` from marker-free payload identity, then persists final payload digest. Adapter requires complete exact-scope preflight absence, validates run marker/repository/workflow/ref/input commit/run attempt/status, performs one postflight lookup, treats conflicting marker or ambiguous send as UNKNOWN, and never replays. Default host registers no network transport. M11/OpenClaw/M12 and polling scheduler remain missing.
- `runalith-sandbox`: Bubblewrap-only local process backend; network namespace isolation, read-only executable roots, bounded writable workspace/scratch, explicit environment allowlist, timeout and output caps. Also includes an isolated expiring one-use workspace-write capability and immutable content-addressed receipt primitive. Workspace path checks remain TOCTOU-vulnerable to hostile concurrent directory replacement; filesystem mutation and receipt persistence are not atomic; caller must enforce approval/plan/role authorization. No unsandboxed fallback.
- `runalith-protocol`: strict COS-AP v1 envelope parsing, versioned Governance approval request/receipt contracts with exact candidate/plan/evidence binding, plus AGG checkpoint v2 original-byte JSON parsing, RFC 8785 JCS canonicalization, and domain-separated SHA-256 digests. Shared Node/Python vectors cover checkpoint canonicalization, parsing and digest conformance. Governance receipt authentication remains an injected host responsibility.
- `runalith-store`: Rust-owned SQLite schema v20, atomic workflow/graph persistence, immutable node revisions/snapshots, independent monotonic lease owner epochs, append-only attempt/result and authenticated result-inbox ledgers, idempotent lease-renewal history and transactionally reserved execution-fence records with append-only per-observation receipts. UNKNOWN and unverified NOT_STARTED observations retain RESERVED. SUCCEEDED/FAILED and independently proof-verified NOT_STARTED are terminal; unverified terminal release is rejected. No production completion-proof verifier or `WorkerControlAuthority` is wired; the standalone Control host remains deny-all. The Store Governance backend is transaction-aware; verifier and signer remain injected and no production authority is wired. Recovery inspection joins task/result, attempt history, provider intent/observations, session registry/ACL/messages and bounded workflow/task events in one deferred SQLite read transaction; truncation is explicit and causes ownership classification to fail closed. Deterministic synthesis is reconstructed from persisted task/result/attempt/policy/approval/event evidence and retained as an immutable workflow event; unsupported predicates remain UNRESOLVED.
- `runalith-execution-persistence`: physical owner of provider intent/reconciliation types, schema-v3→v6 provider DDL, payload/hash validation, lookup, reserve CAS, finalize CAS and append-only observation SQL. All writes borrow the caller's exact `Transaction`; reads borrow its `Connection`; it never opens a second DB connection. Legacy v5 intents migrate with payload absent and cannot be dispatch-validated.
- `runalith-runtime`: application service for workflow proposal/approval/claim/result lifecycle, immutable catalog/version APIs, trusted-skill verification, policy/contract enforcement, persisted custom workflow compilation, coordinator claim ticks and deterministic synthesis/report events. Catalog identity, trusted skills, approval, worker identity, cancellation, runtime session and result producer verification remain host-injected capabilities. No default/test verifier is a production authority. Missing lease alone is not evidence of worker death; unresolved provider evidence takes precedence over a live session in ownership classification.
- `runalith-control-api`: Part 1 HTTP/JSON boundary over WorkflowService and the Rust Store, plus the `runalith-control` executable. The binary provides explicit `init-db`, read-only `health`, backup-before-migration `migrate-db`, cold `restore-db` into an absent path, loopback `serve`, cooperative `stop`, hash-only bearer principal file authentication, and `/livez`/`/readyz`. Process-level tests exercise startup, real HTTP auth/capabilities, catalog compilation/plan binding, exact replay/conflict, fail-closed worker routes, graceful stop/restart, populated v17→v20 migration backup, cold restore/readback/no-overwrite, SIGKILL recovery and live-server maintenance exclusion. The systemd unit preserves its private runtime directory so offline maintenance uses the same lock inode after service stop. Maintenance commands acquire the Control advisory lock but do not establish the global D-01 writer barrier. The executable is a **D-01 shared-Store compatibility host**, not a separate Control-owned database or production authority composition. Approval, worker/result/cancellation verifiers deny all; skills are rejected unless no-skill catalog paths are used. `CoordinatorLoop` remains a library port to an Execution-owned worker; this executable does not claim or dispatch work.
- `runalith-recovery`: side-effect-free stale-workflow gate and per-attempt ownership classifier. It requires explicit authoritative lease/session/provider observations; unknown evidence remains unknown and ambiguous provider outcomes remain unresolved. Runtime snapshot identity/completeness/freshness is checked. No terminalize, replay or recovery mutation.
- `runalith-trust`: Ed25519 public-key parsing, SPKI SHA-256 fingerprints, Node-compatible five-domain administrator JSON configuration, domain/provider/root disjointness, a separate append-only trust high-water ledger, common signed-envelope verification with explicit-observation gating, signed approval-policy verification, maker attestation/checker vote verification, reviewer registry binding, maker/checker separation, quorum/veto rules, one-use nonce ledger and policy anti-rollback within the caller's SQLite transaction. `runalith-runtime::TrustApprovalVerifier` adapts exact Node schema-v1 evidence to Store approval/revalidation and requires an injected current-snapshot `CandidateBindingResolver`; the default host still uses deny-all and no production trust is configured. External checkpoint continuity and reviewer-identity event lifecycle remain unimplemented.
- `runalith-mcp`: Rust stdio server, current MCP `2026-07-28` discovery/metadata flow, legacy `2025-11-25` handshake, 62 registered Rust tools currently observed. The current dirty checkout does not compile this crate: `src/lib.rs` references unresolved `valid_json_rpc_request_id` and `mutating_tool_call` symbols (see current validation below); that out-of-scope file was not changed. Includes durable custom role/workflow catalog operations, typed artifact-content validation, read-only resource recommendations over Store-backed catalog entries, trusted-skill resolver injection, policy/contract operations, persisted custom workflow previews, read-only ready-task scheduling, workflow inspection, authenticated result inbox, synthesis/reporting, agent-session/ACL/delivery lifecycle, recovery quarantine, event-chain verification, graph capture/snapshot/search, Plan Graph and Execution Graph projections, optional sandbox task execution and opt-in provider reconciliation. Node MCP reference remains 75 tools; registered count is not behavioral parity.

The current Rust implementation remains local-only: no legacy database connection, no provider adapter registration in the default MCP host, no production trust-root provisioning, production dispatch or cutover. The Control executable is a local HTTP compatibility host over the shared D-01 Store; it does not resolve the ADR 0003 ownership conflict. `CatalogAuthorVerifier`, `TrustedSkillResolver`, `TaskResultProducerVerifier`, approval and worker verifiers have explicit injection boundaries, but no production host wiring is provisioned. The standalone Control binary defaults approval, worker, result and cancellation authority to deny-all and has no worker-control backend. An opt-in concrete GitHub Actions HTTP adapter exists but has no production configuration or registration. Bubblewrap task execution is capability-injected and disabled by default. Trust configuration and ledger APIs are not connected to production environment variables or live trust databases. AGG external checkpoint custody and signed authority remain unconfigured.

`.github/workflows/ci.yml` now includes a separate clean-clone Rust job pinned to MSRV 1.85.0. It fetches the locked dependency closure, then runs formatting, offline workspace tests and Clippy. This job is not independently verified until GitHub Actions executes it on a clean runner.

## Run the standalone Control compatibility host

See [`docs/control-operations.md`](docs/control-operations.md) and the systemd/example configuration in [`deploy/control/`](deploy/control/). Build with `cargo build --release --locked -p runalith-control-api`. The `runalith-control` binary supports `init-db`, `health`, `migrate-db BACKUP_PATH`, `restore-db BACKUP_PATH`, `serve`, `stop`, and `version`. Database creation, migration and restore are explicit; startup never migrates. `migrate-db` creates and verifies a private `VACUUM INTO` backup before invoking the Store migration. `restore-db` validates a private healthy schema-v20 snapshot and atomically publishes it only to an absent path; existing databases and SQLite sidecars are never overwritten or discarded. Its real-process acceptance test proves persisted workflow readback and no-overwrite behavior on a disposable fixture; it does not replace an external D-01 writer fence or production rollback rehearsal. Migration acceptance exercises a populated schema-v17 backup upgraded to v20. The Store separately tests populated reconstructed v8→v20 and v18→v20. Run `deploy/control/smoke-test-install.sh target/release/runalith-control` to verify temporary binary installation, rendered systemd unit syntax/security, process startup, HTTP probes/auth, crash recovery, graceful stop and database persistence. When a user systemd manager is available, the harness also activates a transient user-scope service; it does not install or activate the system-scope host unit.

The bearer file stores only SHA-256 digests and fixed capability lists; it never stores plaintext credentials. Plain HTTP binds loopback only. `/livez` checks handler liveness; `/readyz` checks Store schema/integrity/foreign keys and rejects the D-01 checkpoint quarantine marker. Readiness is not an assertion of upstream trust, worker, provider or production authority.

**Deployment limitation:** this executable still opens the shared D-01 schema-v20 Store. Its worker Control backend is not configured, so `/v1/worker/*` returns 503; approval, result-producer and cancellation verifiers deny all. It is useful for API/process integration, not production dispatch or independent Part 1 rollout. Do not migrate while any other D-01 process can access the file; this service's PID check is not a global writer barrier. Restore/rollback requires a fully quiesced D-01 maintenance procedure and has not been production-tested.

## Run the isolated MCP host

The Rust binary also provides read-only local operations:

```sh
cargo run -p runalith-mcp --offline -- --version
cargo run -p runalith-mcp --offline -- config inspect
cargo run -p runalith-mcp --offline -- health
```

`config inspect` reports configuration presence only; it never prints secret values. `health` opens an existing schema-v20 DB read-only, checks SQLite `quick_check` and durable workflow/task/provider/attempt/session/message/catalog/policy/trust/result-inbox/trusted-skill/checkpoint/Governance-decision counts, and never creates a directory/database or runs migrations. Exit code `2` means NOT_INITIALIZED/BLOCKED. It does not claim external runtime liveness, provider health, host activation or production authority.

```bash
cd rust
RUNALITH_RUST_DATA_DIR=/path/to/a/new/private/directory cargo run --locked -p runalith-mcp
```

The host creates `workflow-rust.db` in the configured directory (default: `$HOME/.runalith/rust-runtime`). It refuses to overwrite an existing database, requires private directory/file permissions on Unix, and opens only schema version 20 from this Rust workspace. Rust schema v2–v20 upgrades require explicit `Store::migrate_existing_rust_database`; host startup never migrates a database. The host never migrates the legacy Node database. The default approval verifier rejects every approval. No concrete provider adapter is registered, and no MCP tool dispatches provider work. Session message tools persist transport intent and receipts only; they do not invoke external delivery transport.

Optional sandbox execution requires `RUNALITH_ENABLE_SANDBOX_EXECUTION=1` plus `RUNALITH_BWRAP_BINARY`, `RUNALITH_SANDBOX_WORKSPACE_ROOT`, and semicolon-separated `RUNALITH_SANDBOX_EXECUTABLE_ROOTS`. Optional `RUNALITH_SANDBOX_ALLOWED_ENV`, `RUNALITH_SANDBOX_TIMEOUT_SECONDS`, `RUNALITH_SANDBOX_OUTPUT_LIMIT_BYTES`, and `RUNALITH_ARTIFACT_STORE_DIR` narrow/configure the backend. Without the explicit enable flag, `workflow_sandbox_execute` fails closed. Even when enabled, the default reject-all approval verifier prevents task execution.

## Part 1 Control API boundary

`runalith-control-api` provides both an HTTP library and the `runalith-control` executable. The library deliberately does not fabricate credentials, approval evidence, worker identities, result-producer attestations or trusted-skill roots. `ControlApi::open_existing` requires an existing private Rust schema-v20 database; it performs no migration or implicit database creation. `ControlApi::from_store` supports explicit host composition. Routes cover `/livez`, `/readyz`, `/health`, `/v1/workflows`, `POST /v1/workflows/from-catalog-plan`, `/v1/catalog/{roles,workflows}`, `/v1/plans/{plan_id}`, `/v1/policies`, per-workflow approval/admission/synthesis/cancellation/events/success-contract/policy attachment, coordinator tick, task-attempt/recovery inspection and authenticated result-envelope ingestion.

The Store migration test reconstructs an exact schema-v8 boundary from the current migration DDL, populates workflow/session/ACL/message rows, then exercises the explicit v8→v20 migration path and verifies retained identities plus workflow event-chain integrity. It is not an externally sourced legacy Node database or production migration/rollback proof.

Every request requires a host-authenticated Bearer credential and host-issued capability. Catalog create/compile and catalog-plan instantiation require `TrustedSkillResolver`; approval, coordinator claims, result ingestion and cancellation independently pass through their respective host verifiers and Store transaction checks. Missing trusted-skill authority returns 503; deny-all approval authority cannot approve/admit/claim. `POST /v1/workflows/from-catalog-plan` requires a body `idempotency_key`; exact replay returns the same workflow, changed content under the same actor/key conflicts, and the binding is stored in the append-only event journal. `GET /v1/workflows/{workflow_id}/tasks/{task_id}/recovery` requires `workflow.recovery.read` and returns a read-only attempt snapshot with `UNRESOLVED` disposition; it never settles or releases a lease. Other mutations retain each Store operation's own idempotency/conflict semantics; no universal HTTP `Idempotency-Key` header ledger exists. Plain HTTP refuses non-loopback binds; place a trusted TLS terminator in front and keep this listener on loopback. `serve_until` provides bounded connection concurrency and cooperative shutdown. `CoordinatorLoop` limits claims per tick, checks shutdown between claims, and calls only explicit `ExecutionWorker::accept_claim`. It does not execute, dispatch or automatically retry. If worker handoff fails after claim, lease remains durable and unresolved for host reconciliation.

The standalone executable is locally process-tested and transiently systemd-user-service-tested, but is not independently production-released. It uses a private hash-only auth allowlist and deny-all approval, worker, result and cancellation verifiers. Its `/v1/worker/*` routes return 503 without `WorkerControlAuthority`; it does not dispatch. Process regressions prove concurrent-start exclusion, failed-bind cleanup, and failure-startup lock release. Store races cover concurrent exact/conflicting cancellation requests and cancellation-vs-claim; direct/coordinator claim race and mixed-path fairness. The install smoke activates a transient user-scope unit and checks SIGKILL auto-restart, clean restart and `ExecStop`; it does not install or activate the system unit. The executable still opens the shared D-01 schema-v20 Store and therefore does not satisfy a Control-owned DB boundary. Executing cancellation persists a request only, retains active leases, blocks new claims and projects `settlement_status=UNRESOLVED` until Execution-owned stop/settlement proof exists; standalone Control has no such verifier and responds 503 without mutation. The current Governance contract records D-01 as approved: workflow and security-critical trust projections share one physical SQLite database for transaction consistency. This has not been reconciled with ADR 0003's target of per-deployable database ownership; see [`docs/control-db-ownership-analysis.md`](docs/control-db-ownership-analysis.md), and do not split the database until the decision owner resolves that conflict. Part 1 stays PARTIAL and rollout BLOCKED.

The HTTP boundary and public `ControlApi::handle` decoder both enforce a 1 MiB request-body limit. Raw JSON is scanned recursively for duplicate object keys before typed decode, including nested keys and duplicate names whose JSON escape spellings decode to the same string. The parser also rejects duplicate framing/security headers, `Transfer-Encoding`, malformed or duplicate `Content-Length`, invalid request-line separators, oversized headers and unknown typed fields. These checks do not replace TLS termination or the host identity/authority boundary.

The quota crate provides a root-only `runalith-quota-integration` harness. Run `--preflight` against a dedicated ext4/XFS mount with active `prjquota`/`pquota` before the destructive byte/inode exhaustion and recovery modes; see [`crates/runalith-linux-quota/README.md`](crates/runalith-linux-quota/README.md). A successful build or a failed preflight is not kernel quota integration evidence.

### Exact custom catalog plan instantiation

`POST /v1/workflows/from-catalog-plan` accepts an exact persisted `plan_id`, an actor-scoped `idempotency_key`, `title`, and `goal`. It requires `workflow.create` plus a host-injected `TrustedSkillResolver`; the caller cannot choose the workflow instance ID or claim a catalog slug. Store reloads and digest-verifies the exact catalog version, recompiles it with current trusted-skill verification, derives the task projection, and appends `workflow.catalog_plan_bound` in the same `BEGIN IMMEDIATE` transaction as workflow creation. The workflow instance ID is derived from the authenticated actor and idempotency key. Exact replay returns the original workflow; changed request content under the same key conflicts. No schema migration was needed. The success evaluator resolves `workflow_id_equals` only from this verified append-only binding; generic/unbound proposals remain `UNRESOLVED`, never false-PASS from caller metadata.

### Part 1 — Workflow Control implementation status

The current Part 1 slice persists immutable custom role/workflow versions, exact role pins and compiled plans; host-resolved skill references are pinned by exact identity/version/content digest and revalidated at workflow create/update/compile. Policy packs are immutable/versioned with content digests, exact workflow attachments and append-only audit events; approval pins a composed success-contract snapshot to the immutable plan, and approval/admission/claim/completion revalidate exact references transactionally. `Store::admit_workflow` persists an idempotent `workflow.admitted` checkpoint under `BEGIN IMMEDIATE`; missing approval authority fails before mutation and admission is not dispatch authorization. Success-contract predicate IDs match Node's 80-character slug limit; policy rule IDs retain their independent 39-character namespace limit. Text trimming, null defaults and `criteria` alias precedence match Node's normalizer under direct Rust/Node tests. Node oracle fixture `success-contract-predicate-v1-node.json` records 15 cases across all 11 predicate types. A new persisted Store-path test compares 12 cases against the Node oracle after policy attachment, approval, admission, claims and result persistence; three negative references are rejected at policy attachment, while execution/catalog/artifact cases remain UNRESOLVED without authoritative typed evidence. This is partial differential coverage, not full evaluator parity. Result ingestion has immutable event IDs, producer provenance and payload digest in a durable inbox; producer verification, task/attempt/plan fencing, result persistence and event append share one writer transaction. Duplicate replay reauthenticates producer and rechecks provenance, plan, historical lease/worker, inbox payload, task result, journal and event-chain integrity. Deterministic synthesis reconstructs task, attempt, result-inbox, approval, policy/contract and source-event provenance; report is retained in the append-only event journal and PASSED requires COMPLETED plus passing persisted predicates. `workflow_synthesize` exposes this operation. The `runalith-control-api` provides a host-composed HTTP boundary, policy/catalog/workflow routes, capability authorization and read-only recovery observations. Bearer scheme parsing is HTTP case-insensitive; malformed, duplicate or out-of-range `limit` query parameters are rejected rather than silently defaulted. Its `CoordinatorLoop` performs bounded repeated atomic claims and hands exact leases to an injected worker port; it never dispatches or retries. `CatalogAuthorVerifier`, `TrustedSkillResolver`, `TaskResultProducerVerifier`, approval, worker and cancellation verifiers remain host-injected; production host wiring is absent. Recovery binds lease observations to exact immutable attempt-ledger identity; missing historical identity remains UNKNOWN. The standalone `runalith-control` binary and actual-process acceptance harness cover HTTP hosting, auth/capability behavior, catalog-plan idempotency, graceful and SIGKILL restart, cold restore and migration backup. This remains **PARTIAL Part 1**: no resolved Control-owned database boundary, production authority wiring, deterministic local-step executor, cancellation/lease settlement, authoritative recovery disposition or full Node differential lifecycle parity. Recovery API remains read-only.

The recovery crate provides pure stale-workflow and per-attempt ownership classifiers. `WorkflowService::bind_runtime_session` requires an injected host attestation verifier and persists the exact runtime/session/lease/worker/attempt binding in the append-only event journal after an IMMEDIATE-transaction lease recheck. `classify_task_attempt_ownership` reads that binding with current task/result/provider/session/message observations and journal events, then validates the matching runtime inventory snapshot. Owner epoch is a separately persisted monotonic fencing column advanced with lease CAS; current claim issuance advances it in lockstep with attempt count. `classify_and_record_recovery_decision` requires an injected `RecoveryDecisionVerifier`; Store rechecks task/epoch/lease/plan/provider/session and verifies the complete workflow event hash chain under `BEGIN IMMEDIATE` before appending an idempotent immutable decision observation. This is audit-only, not a lifecycle disposition. A present lease or live session proves an observed owner only when no unresolved provider outcome exists; unresolved provider evidence takes precedence. Missing lease alone is UNKNOWN, becoming authoritative absence only with a persisted terminal result and a complete bound-session inventory. ACCEPTED provider intent remains UNRESOLVED; more than 500 relevant task journal events forces UNKNOWN. No production host verifier/inventory adapter, Node runtime inventory integration, artifact/provider terminal-result joins, atomic lifecycle settlement or replay authority is implemented; these gaps prevent recovery parity.

The direct Store claim path now journals the exact `ownerEpoch` and refreshes workflow `updated_at` on every claim, including claims made after the workflow is already `EXECUTING`. `direct_task_claim_journal_event_binds_owner_epoch` checks the immutable event/attempt identity. `direct_and_coordinator_claim_race_commits_exactly_one_fenced_attempt` races two independent SQLite connections through both claim APIs and proves one attempt/lease/event wins. `direct_claim_refreshes_workflow_fairness_timestamp_for_coordinator` reproduced and verifies the mixed-path fairness fix: later coordinator ticks rotate to the workflow that has waited longer.
