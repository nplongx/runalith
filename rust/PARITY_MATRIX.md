## Three deployables / eight workstreams

The deployment target remains exactly three deployables under [ADR 0003](../docs/adr/0003-three-part-rust-deployment.md). Implementation is now partitioned into [eight parallel workstreams](EIGHT_PART_PARALLEL_PLAN.md) with [individual briefs](workstreams/README.md). This does not create eight services or change deployment topology. It does not describe the current topology: only a subset of host binaries exist, `runalith-runtime` composes cross-cutting concerns, and execution/provider crates still depend directly on `runalith-store`.

| Deployable boundary | Initial crate ownership | Current extraction gap |
|---|---|---|
| Workflow Control | `runalith-domain`, `runalith-store`, `runalith-runtime`, `runalith-recovery`, `runalith-control-api` | Part 1 HTTP/JSON API and `runalith-control` compatibility host exist; routes expose catalog/policy/plan/workflow/approval/admission/scheduling/result/synthesis and read-only recovery. Host principal/capability and domain verifiers are injected. Bounded loopback HTTP and continuous bounded coordinator loop exist; coordinator hands durable claims to an explicit worker port and never executes or retries. Still missing: isolated Control-owned schema/database, production verifier and worker-authority wiring, Node-equivalent deterministic local-step orchestration and authoritative cross-part recovery disposition. Combined schema-v20 Store still contains cross-part records. |
| Execution Workers | `runalith-execution`, `runalith-sandbox`, `runalith-providers`, `runalith-artifacts`, `runalith-execution-persistence` | Remove direct Store dependencies; isolate provider/session/worker persistence; add durable outbox/inbox, admission and full polling/result collection |
| Governance & Interface | `runalith-trust`, `runalith-agg`, `runalith-protocol`, MCP/API gateway | Isolate trust/AGG ledgers; make MCP call service contracts rather than compose internal modules; implement external checkpoint continuity and complete tool parity |

Workstream mapping: Workflow Control = 1 Catalog/Compiler + 2 Lifecycle; Execution Workers = 3 Worker/Sandbox + 4 Provider Effects + 5 Sessions/Artifacts; Governance & Interface = 6 Governance Authority + 7 AGG Evidence/Checkpoint + 8 Gateway/Protocol. The complete scope, non-goals, contracts, cross-workstream dependencies and acceptance gates live in `EIGHT_PART_PARALLEL_PLAN.md`.

Crate assignment is a starting ownership map, not proof that dependencies are already clean. Cross-part DB access is prohibited in the target. Three independent binaries, service health/observability, independent clean-clone pipelines and per-part rollback evidence remain unimplemented.

## Priority order

1. **Contract and ownership extraction:** define versioned Control/Execution/Governance APIs, event envelopes, durable inbox/outbox and isolated persistence ownership. Required before separate processes.
2. **Workflow Control parity:** production host wiring for catalog identity/trusted skills/result producers, full Node success-predicate semantics, deterministic local-step orchestration, Node differential synthesis/reporting, authoritative recovery disposition and independent process/database ownership.
3. **Execution Workers parity:** worker admission, process/session lifecycle, race-resistant sandbox, provider polling/result collection, artifacts and ambiguity-safe reconciliation.
4. **Governance & Interface parity:** approval binding to current candidates, reviewer identity lifecycle, production trust configuration, external checkpoint continuity, AGG evidence/Phase 2/3 and all MCP schemas/handlers.
5. **Independent deployment proof:** clean-clone build/test per deployable, contract compatibility, network-failure/restart/concurrency tests, observability and per-part rollback.
6. **Import, shadow comparison and cutover:** only after feature/security parity; separate owner authorization required.

## Port slices added 2026-11-01

The new `runalith-agg::graph_contract_v1` module validates original JSON bytes against Node's schema-v1 graph contract, normalizes all five metric provenance records, validates typed conditional recovery edges, sorts nodes/edges/references, computes the same ordered compact-JSON SHA-256 graph hash, and exposes a projection into the current Rust search API. `tests/fixtures/adaptive-goal-graph-v1-canonical.json` is generated by the Node reference and consumed by Rust tests. The projection still omits path-level provenance from search results and does not port Node candidate-ID semantics or recovery resolution.

The `runalith-protocol::agg_checkpoint_v2` module separately implements strict I-JSON/JCS checkpoint parsing and domain-separated digests. AGG graph v1 permits negative zero and normalizes it to positive zero to match Node JSON.stringify; checkpoint v2 continues to reject negative zero.

The new `runalith-recovery` crate implements only a pure decision for stale workflow terminalization eligibility. It requires stale executing state, authoritative runtime inventory with no linked live session, and a successful durable-ownership query showing neither active leases nor unresolved provider outcomes. Unknown inventory/ownership defers. A positive result still requires all checks to be repeated inside a separate atomic persistence command. It does not prove individual task death and does not mutate or replay anything.

The GitHub Actions provider slice now has a concrete opt-in HTTP transport over a bounded curl executor. It reads bearer credentials from host environment, passes curl config over stdin rather than argv, validates exact immutable target/run identity and input commit, refuses secret-bearing payloads, requires complete preflight pagination before one dispatch, and performs one postflight lookup after acceptance. Runtime derives the durable intent marker without a self-referential payload hash, then persists the final payload digest. A conflicting run with the exact marker but mismatched immutable identity is UNKNOWN, never absence. The default host registers no provider adapter. Tests cover authenticated transport requests through a mock executor, pagination completeness, marker collision, ambiguous send, postflight visibility, payloadless legacy rows and secret rejection.

The MCP response boundary now recursively redacts secret-bearing structured keys and embedded provider-token patterns for workflow projections, event records, graph/snapshot outputs and provider reconciliation results. The workflow-get regression proves nested token, API-key and client-secret fields are redacted while ordinary fields remain unchanged. This does not replace per-tool data-minimization or a full secret-classification audit.

`runalith-recovery::manager::RecoveryManager` provides a pure classifier and validates runtime snapshots when given an exact linked session. `WorkflowService::bind_runtime_session` now requires an injected `RuntimeSessionBindingVerifier`; Store rechecks the exact RUNNING attempt/lease/worker under an IMMEDIATE transaction and appends an immutable session-binding event. `owner_epoch` is currently the monotonic attempt number; no separate lease epoch column exists. Recovery reads that binding with task/result/provider observations and a bounded event slice under one SQLite read transaction, then validates the matching runtime snapshot. More than 500 relevant events forces UNKNOWN. A missing lease is authoritative only alongside a persisted terminal result; absence alone never implies worker death. ACCEPTED provider dispatch remains unresolved until terminal provider reconciliation exists. There is still no production host verifier/inventory adapter, complete historical attempt/artifact ledger or atomic recovery decision command.

The new `runalith-trust` crate implements Ed25519 SPKI parsing/fingerprinting/signature verification, five-domain administrator JSON parsing, exact scope and cross-domain provider/root disjointness, key validity/revocation checks, a dedicated append-only trust-config high-water ledger, and common signed-envelope validation. The ledger is separate from workflow SQLite, refuses unknown existing schema versions without migration, records rejection events after rollback, and exposes read-only assert-observed checks. A Node-generated Ed25519 envelope fixture verifies canonical payload/signature/hash parity. Domain-specific policy, maker, reviewer decision, quorum, nonce replay and policy high-water checks remain unported. No production trust configuration or trust database was loaded or mutated.

`runalith-domain::custom_workflow` now separates Node custom roles from built-in agent contracts. It validates reserved IDs, explicit custom role versions, typed artifact contracts, capability/tool/permission allowlists and skill IDs supplied by a separate catalog. Rust Store persists immutable role/workflow versions, exact role pins, append-only catalog events and compiled plan snapshots; MCP exposes catalog CRUD and persisted preview. A Node-generated fixture from `custom-workflows.js::previewCustomWorkflow` verifies exact canonical plan bytes and SHA-256. MCP catalog mutations now require a host-injected `CatalogAuthorVerifier`; no verifier, malformed principal or `mcp:unattributed` is rejected before mutation. This is an authority interface, not a provisioned production identity source. Trusted skill catalog integration, persisted policy enforcement, plan approval integration and coordinator consumption remain missing.

`runalith-agg::discriminator` ports Node Phase 2 discriminator model v2 validation, seven-feature extraction and standardized logistic scoring. A Node-generated fixture from `trainFixture()` verifies exact model hash, features and score. Scores remain `model_estimate_unverified`. `runalith-agg::phase2` validates the supplied Phase 1 result against a fresh bounded search, rejects forged/stale candidate sets, then ranks candidates deterministically using discriminator scores and stable plan-ID tie-breaking. `runalith-agg::mcts` adds a deterministic, digest-seeded, bounded shadow MCTS kernel with graph-transition, prerequisite, conflict and no-revisit constraints; it uses the discriminator only as a rollout estimate. MCP exposes both as read-only tools over the latest immutable graph snapshot and validates the full model v2 object before scoring. Both outputs explicitly remain non-authoritative: evidence status is `UNKNOWN`/unverified, `exhaustive=false` for MCTS, and execution/dispatch authorization are false. This is algorithmic Phase 2/3 groundwork, not parity completion: no training/evaluation pipeline, authoritative membership/evidence verifier, checkpoint-linked graph proof, or production execution integration exists.

`runalith-sandbox::workspace_write` adds an isolated expiring one-use scoped write capability, SHA-256 base precondition and immutable content-addressed receipt. It is not wired to approval/plan persistence; callers must authorize capability issuance. Path-based checks remain TOCTOU-vulnerable to hostile concurrent parent replacement, and filesystem mutation plus receipt persistence are not atomic.

Approval persistence was hardened in this slice: Store::approve now accepts an untrusted ApprovalRequest and host verifier, not a caller-built Approval. The verifier runs under the active SQLite IMMEDIATE transaction. The same verifier revalidates persisted approval inside task-claim and provider-intent reservation transactions. A failing verifier rolls back its test nonce write; default DenyAll rejects direct store approval. This closes the previous direct-store bypass and pre-transaction verification race, but no production trust verifier or nonce ledger is provisioned.

The new `runalith-recovery` crate implements only a pure decision for stale workflow terminalization eligibility. It requires stale executing state, authoritative runtime inventory with no linked live session, and a successful durable-ownership query showing neither active leases nor unresolved provider outcomes. Unknown inventory/ownership defers. A positive result still requires all checks to be repeated inside a separate atomic persistence command. It does not prove individual task death and does not mutate or replay anything.

The Part 3 follow-up adds `runalith-trust::governance_service`, an independent application service boundary with authenticated Control requests, strict raw evidence parsing/JCS digest binding, a transactional consume-and-persist backend contract, and exact request-bound signed receipts. It imports no Runtime or Store. It does not yet include a concrete deployable Governance database/backend, because the approved D-01 projection requires one physical SQLite database and the current composition has no Governance-owned service host or transaction coordinator.

`runalith-trust::trust_lifecycle` adds administrator-authenticated trust provisioning and an optimistic-CAS repository contract. Transition validation checks monotonic versions, immutable SPKI/key identity, root tombstones, revocation non-reversal, canonical validity timestamps and fingerprint integrity. Existing trust ledger remains append-only. No organization-issued production credentials, trust anchors, reviewer registrations, or repository adapter were created.

`runalith-agg::custody` adds D-01 checkpoint saga contracts for authority prepare/finalize/abort/status/head/outstanding operations, independent attestation and receipt verifiers, nonce-ledger persistence, fenced transition-gate ownership, and local intent/anchor/quarantine repository operations. The verification kernel binds canonical projection/checkpoint digests, operation/audience/challenge context, predecessor sequence and database identity; absent verifier/ledger/authority evidence stays UNKNOWN. This is a contract and validation foundation, not an external authority implementation. The normative projection manifest and complete authorization writer inventory are still prerequisites; no digest formula here substitutes for the approved aggregate envelope.

`runalith-protocol::mcp_service_v1` and `runalith-mcp::service_gateway` add a versioned transport-neutral Gateway contract with authenticated principal context, explicit capability/side-effect class, mutating idempotency, exact response binding and distinct read-only/mutating service methods. Negative tests prove authorization denial prevents invocation and read-only routes cannot call the mutation API. The active stdio host remains directly composed with Runtime/Store pending a full handler migration and independent Control/Execution APIs.
