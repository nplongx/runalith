# Rust rewrite: three deployables, eight parallel workstreams

**Status:** Architecture target accepted for planning; implementation and production rollout remain incomplete and unauthorized.
**Scope:** Preserve the accepted three-deployable topology while dividing implementation ownership into eight parallel workstreams. See [EIGHT_PART_PARALLEL_PLAN.md](EIGHT_PART_PARALLEL_PLAN.md) and [workstream briefs](workstreams/README.md). This document retains the original three-deployable implementation history and current evidence; it does not change behavioral-parity or authority requirements.

**Current repository snapshot (2026-11-07):** implementation and production rollout remain incomplete and blocked. The current cross-cutting local test/build results and separate workstream ownership limitations are in [`../docs/STATUS_2026-11-07.md`](../docs/STATUS_2026-11-07.md). This dated implementation plan is not evidence of a current clean build, owner ratification, or production deployment.

## Decision

The rewrite is split into three deployables with separate data ownership and versioned contracts:

1. **Workflow Control** — owns workflow definitions, plans, orchestration and lifecycle decisions.
2. **Execution Workers** — owns execution attempts at the process/provider boundary, sessions, artifacts and external-effect reconciliation.
3. **Governance & Interface** — owns trust/approval verification, AGG/evidence governance and the user/operator interface.

Each part must be independently buildable, testable, deployable, observable and rollbackable. A part may be released without releasing the others when its contract remains backward-compatible. This is a target topology, not a claim that current crates can already run as three processes.

**Decomposition rule:** the three items above are deployment groups. Parallel implementation ownership is now eight workstreams: Workflow Control is workstreams 1–2; Execution Workers is workstreams 3–5; Governance & Interface is workstreams 6–8. The historical headings and status references below retain the previous Part 1/2/3 naming for traceability. They are not a competing eight-service topology. ADR 0003 remains the deployment authority; no database split or cutover is authorized by this documentation update.

## Deployable A — Workflow Control (historical Part 1; workstreams 1–2)

**Purpose:** Decide *what* should happen, *in what order*, under *which approved immutable plan*, and whether workflow/task state may advance.

**Owns**

- Workflow catalog, built-in/custom roles, custom workflow versions and trusted skill references.
- Proposal, preflight, typed inputs/outputs, policy packs, success contracts and deterministic plan compilation.
- Immutable plan snapshots and plan hashes.
- Workflow/task/job lifecycle, dependency gates, task attempts, lease owner epochs and lifecycle event journal.
- Coordinator, admission, scheduling decisions, synthesis/reporting and recovery disposition orchestration.
- Import mapping into a new Control-owned database; never mutate the legacy Node database.

**Rust crate starting set**

- `runalith-domain`
- `runalith-store` (workflow/task/lease/event ownership only after persistence extraction)
- `runalith-runtime` (control application services after adapter extraction)
- `runalith-recovery`

**Required interfaces**

- Accept versioned workflow/role definitions and return immutable plan identity plus digest.
- Accept approval evidence reference and exact candidate/plan/action binding; reject absent, stale, mismatched or unverifiable authority.
- Issue a fenced task-claim envelope containing task, immutable plan digest, attempt, owner epoch, deadline and idempotency identity.
- Consume execution result/reconciliation events idempotently; advance lifecycle only after validating exact lease/attempt/plan lineage.
- Expose read-only workflow/task/attempt/recovery projections.

**Data boundary:** Control DB is authoritative for workflow/task state, task lease epochs and lifecycle event order. Execution and Governance must not write its tables or open its SQLite file.

**Independent acceptance:** Node differential fixtures for catalog/compile/state transitions; transaction/crash/concurrency tests for claim and lifecycle CAS; stale/mismatched approval and lease negative tests; replay-safe event ingestion; read-only import and restore/rollback proof.

**Implementation status (2026-11-03): Partial, not independently deployable.** Rust Store schema v20 persists immutable custom role/workflow versions, exact role-version pins, digest-verified compiled-plan snapshots, immutable policy pack versions, exact workflow attachments, composed success-contract snapshots and append-only policy/catalog events, plus lease-renewal/execution-fence and cancellation-settlement recovery ledgers. Governance decision/event and signed-receipt persistence now exist behind injected verifier/signer contracts; no production authority is wired. Policy definitions are validated and semantically composed deterministically; exact pack/contract digests and immutable plan pins are rechecked at approval, admission, claim and completion. Admission is an explicit persisted checkpoint (`Store::admit_workflow`): it uses `BEGIN IMMEDIATE`, revalidates approval/policy/contract pins, records one idempotent `workflow.admitted` event and fails closed before mutation when approval authority is unavailable. Claim independently repeats revalidation; admission does not authorize dispatch. Node-generated golden fixtures verify policy composition and four persisted PASS predicates; a Rust regression persists remaining execution/artifact predicate families as UNRESOLVED instead of rejecting the contract at attachment. Success-contract predicate IDs follow Node's 80-character slug bound, independently from the 39-character policy-rule namespace bound. Text trimming, null defaults and `criteria` alias precedence match Node's success-contract normalizer under direct Rust/Node tests. `workflow_id_equals` now PASS/FAIL compares the exact catalog workflow slug only for workflow instances created from an immutable custom catalog plan through the authenticated Control API; the workflow/plan binding lives in the append-only event journal and is rechecked against the catalog plan digest and exact derived task projection. Generic proposals and legacy instances without that binding remain UNRESOLVED rather than comparing the unrelated `job_` instance ID or trusting metadata. Execution/artifact predicates remain UNRESOLVED without authoritative evidence. Host-owned `TrustedSkillResolver` resolves exact role skill references to canonical identity/version/content digests; pins are retained per immutable role version and revalidated when workflow versions are created/updated, compiled and bound to a workflow instance. MCP catalog create/update/preview requires injected `CatalogAuthorVerifier`; missing verifier, invalid principal and `mcp:unattributed` fail closed. No production identity or skill trust authority is wired. Result ingestion accepts immutable event ID, producer ID/provenance and payload digest; host `TaskResultProducerVerifier`, payload binding, exact workflow/plan/task/attempt/lease checks, inbox insertion, result persistence and event journal append share one IMMEDIATE transaction. Duplicate replay reauthenticates producer provenance and rechecks stored inbox payload integrity, task result projection/hash, corresponding task-result event, current immutable plan digest, exact historical lease/worker binding, matching inbox journal event and full event-chain integrity before acknowledging; changed or unavailable authority rejects replay. Synthesis reconstructs task, attempt, inbox, approval, policy/contract and event-chain provenance from persisted evidence; a deterministic report is retained in the append-only event journal. PASSED requires workflow COMPLETED and all persisted predicates PASS; unsupported execution/artifact predicates remain UNRESOLVED. `workflow_synthesize` exposes this report. The coordinator remains a bounded repeated atomic claim loop handing durable claims to an injected worker port; it does not implement worker execution, provider dispatch or ambiguous handoff replay. Recovery joins local attempt/provider/session/event evidence and binds lease observations to the immutable attempt-ledger lease ID; missing historical lease identity remains UNKNOWN. No authoritative cross-part recovery disposition is persisted. A standalone `runalith-control` compatibility host now exists over the combined Store. This does not satisfy the accepted separately owned Control database boundary. Remaining Part 1 gaps: full task/retry/catalog/error/scheduling/cancellation/recovery/lease/persistence differential parity, Node-equivalent deterministic local-step execution, task cancellation acknowledgement/lease settlement, authoritative cross-part recovery disposition, production identity/approval/result/worker verifiers, Control-owned schema/process boundary, clean-clone release acceptance, and externally sourced migration/restore/rollback proof.

### Part 1 follow-up — Node Job and workflow-phase differential oracle (2026-11-03)

Node's public `job-store.js` maintains two separate lifecycle layers: `jobs.state/status` and `workflow_runtime_state.phase`. Rust's `WorkflowState` is a coarser native execution lifecycle and is not a lossless substitute for either legacy layer. `rust/scripts/generate-node-workflow-lifecycle-oracle.mjs` executes the actual composed Node `WorkflowStore.transition` and `transitionWorkflowPhase` methods in a private disposable SQLite store and generates `runalith-domain/tests/fixtures/node-workflow-lifecycle-v1.json`. The fixture covers 1,296 Job state/status transition combinations and 144 phase transition pairs, including exact terminal replay, illegal active edges, provider-quiescence preconditions, phase idempotency, error classification and workflow-event delta. `runalith-domain::node_compat` is a pure import/differential model; tests compare every generated case. It does not change runtime persistence, authorize terminalization, or claim parity for task execution, scheduling, provider/session/artifact persistence, cancellation or recovery.

### Part 1 follow-up — Node same-task retry preflight oracle (2026-11-03)

## Deployable B — Execution Workers (historical Part 2; workstreams 3–5)

**Purpose:** Perform an already-authorized task and report what actually happened, including uncertainty. Workers do not create workflow authority or decide that an ambiguous remote effect is safe to repeat.

**Owns**

- Worker admission, execution supervision, local process lifecycle and sandbox policy enforcement.
- Provider adapters, dispatch intents, immutable request payload digests, provider run identity, polling and reconciliation observations.
- Runtime session identity/binding, session ACL and delivery queue/receipt/ACK/UNCERTAIN lifecycle.
- Artifact bytes, content addressing, integrity verification and result evidence capture.
- Worker-local operational state and durable inbox/outbox for cross-service event delivery.

**Rust crate starting set**

- `runalith-execution`
- `runalith-sandbox`
- `runalith-providers`
- `runalith-artifacts`
- `runalith-execution-persistence` (move behind Execution-owned persistence boundary)

**Required interfaces**

- Receive a Control-issued, authenticated and fenced task-claim envelope; verify plan digest, attempt, owner epoch, scope and expiry before execution.
- Obtain/renew authority only through Control contract; never infer worker death from missing lease/session metadata.
- Dispatch provider effects once per durable idempotency identity. Ambiguous send/timeout becomes UNKNOWN and remains quarantined until authoritative reconciliation.
- Emit signed or otherwise authenticated, versioned lifecycle/result events bound to task, attempt, owner epoch, plan digest and artifact digests.
- Provide exact provider lookup, terminal status and artifact/result collection; no automatic replay on ambiguous outcome.

**Data boundary:** Execution DB owns provider intents/observations, worker/session delivery state and execution-specific records. Artifact store owns immutable content. Control owns the authoritative workflow lease and lifecycle state. No shared-table transaction across services; use durable inbox/outbox, idempotency keys and explicit reconciliation.

## Deployable C — Governance & Interface (historical Part 3; workstreams 6–8)

**Purpose:** Establish *who may authorize what*, maintain independently verifiable evidence, and expose product/operator interfaces without owning workflow or worker execution state.

**Owns**

- Trust roots/configuration, key/domain separation, signed-envelope verification, reviewer identity, maker/checker quorum, nonce replay protection and trust high-water ledger.
- Approval policy versions and external checkpoint custody/continuity contracts.
- AGG graph revisions, source evidence, provenance/lineage, verification, candidate search, Plan Graph and review-only Execution Graph proposals.
- MCP stdio/API gateway, tool schemas, resources/prompts, capability filtering, diagnostics and operator-facing read models.
- Operator audit views and evidence export; no implicit authority escalation through the interface.

**Rust crate starting set**

- `runalith-trust`
- `runalith-agg`
- `runalith-protocol`
- `runalith-mcp` (gateway composition only; domain ownership stays in the service APIs)

**Required interfaces**

- Verify approval against exact Control candidate, immutable plan, source snapshot, action scope, reviewer identity and current policy version.
- Return a verifiable decision/evidence receipt; Control independently checks receipt binding before lifecycle mutation.
- Accept immutable evidence/artifact references and provide provenance/verification results; never silently upgrade unverified evidence to trusted evidence.
- Provide MCP/API calls to Control and Execution through public contracts; never connect directly to their databases.
- Keep default host behavior deny-all when trust configuration, verifier, checkpoint continuity or authority evidence is absent.

**Data boundary:** Governance owns trust and AGG/evidence ledgers. Control stores only the approval receipt/reference and exact binding needed for its own lifecycle transaction. Interface/gateway stores no authoritative workflow, execution or trust state.

**Independent acceptance:** signature/canonicalization golden vectors, root/domain separation, key rotation/revocation and anti-rollback tests, nonce/quorum/replay/rollback tests, checkpoint continuity tests, AGG source-byte/provenance fixtures, tool/schema compatibility tests and authorization-negative tests.

## Cross-part contract and dependency rules

```text
                 Governance & Interface
                  /                 \
       approval/evidence         MCP/API gateway
                /                     \
       Workflow Control  <------>  Execution Workers
          owns state          task/result contracts
```

- `runalith-protocol` defines versioned wire envelopes, canonicalization, error vocabulary and compatibility fixtures. Contracts are immutable within a major version; incompatible changes require a new version and a migration window.
- Cross-part messages carry stable IDs, schema version, creation time, producer identity, correlation ID, idempotency key and exact subject binding (workflow/task/attempt/owner epoch/plan digest as applicable).
- Use transactional outbox/inbox and consumer deduplication. Never claim a distributed atomic transaction across the three databases.
- Control is the sole authority for workflow/task lifecycle and lease epochs. Execution is sole authority for what its process/provider adapter observed. Governance is sole authority for trust-policy verification and evidence status. A consumer validates the originating authority's receipt rather than rewriting its state.
- No part may read or write another part's SQLite database, tables, filesystem internals or private Rust modules. Shared code is limited to protocol/domain contract crates with no persistence side effects.
- No circular synchronous dependency. Control may request an approval decision from Governance and issue work to Execution; Execution returns observations/events; Governance verifies evidence supplied by references. MCP is a client/gateway, not a privileged bypass.
- During migration, a single Rust composition root may host these modules in-process for local tests, but it must call the same public interfaces used by separate processes. This compatibility mode does not satisfy independent deployment acceptance.

## Definition of independently deployable

A part is independently deployable only when all are true:

1. It has a versioned public contract and no private DB/module dependency on another part.
2. It builds and tests from a clean checkout independently, with pinned dependency closure and reproducible artifact evidence.
3. It owns and migrates only its own stores; schema compatibility and rollback are tested without reverting durable external facts.
4. It authenticates every cross-part caller/message, validates exact subject binding, and handles duplicate, delayed, missing and out-of-order messages safely.
5. It has independent configuration/secrets, health/readiness, metrics/logging, operator runbook and staged release/rollback procedure.
6. Differential Node parity, negative authorization tests, crash/concurrency tests and owner-approved acceptance are complete for its declared scope.

Passing a crate's unit tests or producing a binary alone is not deployment readiness. Production cutover remains a separate authorization.
