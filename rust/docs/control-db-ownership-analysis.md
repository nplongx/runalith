# Control / Governance database ownership analysis

**Assessed:** 2026-11-03  
**Status:** Option B is the user-directed target architecture as of 2026-11-02. A versioned Owner decision formally superseding D-01 §11.3/§11.4 is still absent; runtime decomposition and migration remain blocked.  
**Scope:** Part 1 / Workflow Control versus accepted Governance D-01 and ADR 0003.

## Executive finding

The current Rust Store implements D-01 as one physical SQLite database with two SQLite connection handles. Governance trust/reviewer lifecycle writes use the dedicated Governance connection; Workflow approval reads the current trust high-water and reviewer registry through the active Workflow transaction. The code checks that both handles resolve to the same SQLite `main` path and, on Unix, the same device/inode, then performs a cross-handle visibility probe.

This is current compatibility implementation, not the accepted three-deployable target. It is not a Control-owned database boundary and it is not proof that the later Governance decision receipt and Workflow approval transition form one cross-part atomic operation. The Governance decision/receipt/nonce operation is atomic inside its current D-01 transaction. The later Workflow approval is a separate transaction which revalidates trust configuration and reviewer evidence. Part 3 contract explicitly describes that distinction.

ADR 0003 requires each deployable to own its database and adopts durable outbox/inbox plus authenticated versioned contracts instead of shared SQL or implicit distributed transactions. The latest Part 3 contract clarifies that D-01 is limited to its approved approval-highwater transaction database; it is not a shared-database exception for the three deployables. The current combined Store therefore does not satisfy the accepted deployment topology. The selected direction is Option B below: retain D-01's coherent local approval-highwater projection inside the Control-owned database, while Governance remains authoritative for trust state and communicates through versioned signed contracts. This preserves a Control-local transaction boundary without granting cross-service database access. The exact projection, freshness/revocation and migration contracts remain open; no live database split or migration is authorized.

## Selected architecture direction — Option B (2026-11-02)

The project owner selected the three-database direction already established by ADR 0003. This does not amend or replace ADR 0003 and does not authorize production migration.

**Decision-record boundary:** the Option B direction was accepted in the project conversation, but the repository still contains no versioned Owner decision that explicitly supersedes the 2026-10-30 D-01 decision register. D-01 §11.4 limits its existing approval to specification/documentation work and requires further authorization before runtime actions, tests that mutate the D-01 topology, migrations or provisioning. Part 3 §278 independently requires a versioned superseding decision before changing the runtime transaction/database boundary. Treat Option B as the target for planning and implementation design only; do not treat this analysis or the chat acceptance as the missing signed/versioned data-ownership decision.

- **Workflow Control** owns its database: workflow/task state, leases, owner epochs, lifecycle journal and the minimum authenticated Governance authorization/high-water projection required for a coherent local approval transaction.
- **Governance & Interface** owns its database and secrets: canonical trust roots/configuration, reviewer identities, policy authority, nonce consumption, decision issuance and receipt signing. It publishes versioned, authenticated projection updates and decision receipts; it never opens or writes the Control database.
- **Execution Workers** owns its database and artifacts: worker inbox/outbox, process/provider observations, session delivery and artifact bytes. It communicates with Control through the Worker Control API; it never opens the Control or Governance database.
- Control's D-01 projection is Control-owned replicated authorization evidence, not Governance's authoritative trust store. Control accepts only authenticated, versioned, integrity-bound updates through its own API/inbox and validates freshness inside the same transaction as the workflow approval transition.
- No service may use cross-service SQL, share SQLite files, or treat a local projection as proof of current remote authority without an explicit freshness/revocation contract.

Before implementing this boundary, owners must ratify: exact projection schemas and version/high-water semantics; signer identity and key rotation; freshness/expiry and revocation race behavior; nonce ownership and replay rules; outbox/inbox delivery, duplicate/conflict and UNKNOWN recovery; approval receipt acceptance/acknowledgement; global writer quiescence for the current compatibility database; and additive export/import, lineage, cutover and rollback evidence. Until then, current schema v20 remains a local compatibility implementation, production authority stays fail-closed, and production rollout stays blocked.

## Current schema-v20 lifecycle addition (Part 1)

Store schema v20 adds a durable Workflow cancellation-request marker and append-only request projection. This is a logical lifecycle correction, not a new database owner or physical partition: the new column/event remains in the same D-01 SQLite file, in the same schema/transaction regime as workflow/task state. For an `EXECUTING` workflow, Control records the cancellation request, blocks new claims and retains active lease IDs/owner epochs. It does not treat a request or transport acknowledgement as proof that a worker process stopped. An exact in-flight result may be persisted against its current lease, but the workflow cannot be terminalized while cancellation settlement remains pending.

The explicit v19→v20 migration scans legacy `CANCELLED` projections and verifies the matching cancellation event, actor/reason, immutable plan binding, `runningLeasesRetained` declaration and full event chain. If task attempts exist, it reopens the projection to `EXECUTING` for authoritative reconciliation while preserving the old lease/epoch and appending a migration reconciliation event. Pre-execution cancellations remain terminal. If the event or provenance is absent/tampered, migration aborts atomically; regression tests prove user_version/DDL/data/lease rollback remains at schema v19. This migration does not prove the external process stopped and does not free the lease.

The current combined-Store topology still does not satisfy the selected ADR 0003 deployment target. Cancellation persistence introduces no second DB, authenticated Governance projection or cross-service transaction. Its eventual settlement still requires an Execution-owned signed process-stop/no-more-side-effects receipt and a defined authoritative lease/lifecycle CAS. Without those contracts, Control leaves executing cancellation unresolved. The schema-v20 change therefore preserves existing same-file atomicity but does not resolve the deployment ownership decision or authorize production migration.

## Source-backed current transaction topology

### Store opens two handles to one physical file

`runalith-store/src/lib.rs`:

- `Store::create_new` and `Store::open_existing` create the Workflow connection and call `open_trust_connection` for the Governance connection.
- `open_trust_connection` canonicalizes the configured path and opens a second read/write SQLite connection with `SQLITE_OPEN_NOFOLLOW`.
- `verify_same_database` compares both `PRAGMA database_list` main-file paths. On Unix it additionally compares `st_dev` and `st_ino`. It writes a unique `store_connection_probes` row through the Workflow connection, reads the row through the Governance connection, and deletes it. A different path, inode or visibility fails open with an invariant error.
- Both connections are configured against the same schema version and same WAL-backed file; they are not independent per-deployable databases.

This verifies physical-file identity at Store open. It does not prove that every external Node/MCP/worker process has been stopped during maintenance; the Control advisory lock only excludes competing Control processes. It also does not make the combined Store the accepted three-database target.

### Governance trust/reviewer lifecycle writes

`runalith-store/src/governance_persistence.rs` documents the lock rule explicitly:

- lifecycle writes use the dedicated Governance connection to the same physical SQLite file and `BEGIN IMMEDIATE`;
- a Governance lifecycle writer must not acquire its connection while a Workflow writer lock is held;
- approval reads do not acquire the Governance writer connection. They use the active Workflow transaction.

`TrustConfigurationRepository::append_if_version` loads the current domain version inside the Governance write transaction, enforces expected-version CAS, validates transition invariants, then appends a new immutable version. Reviewer lifecycle persistence follows the same repository pattern. Dedicated handles avoid a mutex-lock inversion; they do not change database ownership.

### Workflow approval reads current D-01 trust state in its writer transaction

`runalith-runtime/src/lib.rs` `TrustApprovalVerifier::verify` receives `&Transaction` from the Workflow approval operation. It passes that exact transaction to `verify_approval_evidence_envelope`. The trust verifier then calls `TrustConfigurationSet::assert_observed_in_transaction`; the D-01 `TrustConfigurationObserver for Store` implementation queries `governance_trust_configuration_versions` through that transaction and requires exact equality of config version, configuration fingerprint and provider ID. A non-transactional observer call deliberately returns `AGG_TRUST_CONFIG_TRANSACTION_REQUIRED`.

When Governance reviewer registry is required, `TrustApprovalVerifier::verify` also calls `verify_registered_reviewer` with the same transaction. The D-01 `current_reviewer_in_transaction` implementation reads reviewer identity/status/key/version using that transaction, not the separate Governance connection. `d01_approval_reads_all_trust_high_water_inside_workflow_transaction` verifies all five trust domains are observed; the companion test verifies a missing domain fails closed.

In the current compatibility implementation, this gives Workflow approval one SQLite transaction snapshot for workflow state, trust high-water, reviewer registry, verifier nonce consumption and resulting approval persistence. Moving the trust rows to a different DB would remove this exact transaction read unless a new contract replaces it.

### Governance decision receipt is a different atomic transaction

`runalith-store/src/governance_decisions.rs` `StoreGovernanceDecisionBackend::evaluate_and_commit`:

1. Locks the Store Workflow connection and starts `BEGIN IMMEDIATE`.
2. Passes that exact transaction to `GovernanceDecisionVerifier::verify_in_transaction` to validate policy/trust/reviewer state and consume one-use nonces.
3. Signs the receipt while the transaction remains open.
4. Inserts the immutable Governance decision and signed receipt.
5. Inserts the committed decision event.
6. Commits all of those writes together. Exact idempotent replay revalidates the evidence, immutable outcome, receipt and event and returns the original receipt.

This proves atomicity for the Governance decision/receipt/nonce/event unit in D-01. It does **not** make a later Workflow approval call part of the same transaction. Part 3 contract says explicitly that the later Control Workflow approval transition is a separate transaction and is not claimed as one cross-service atomic transition.

## Contract conflict

### ADR 0003 — accepted deployment target

`docs/adr/0003-three-part-rust-deployment.md` is accepted as the target decomposition and assigns:

- Workflow Control ownership of workflow/task lifecycle and lease epochs;
- Execution Workers ownership of process/provider/session/artifact execution facts;
- Governance & Interface ownership of trust roots/policies, approval verification, AGG/evidence/checkpoint custody and gateway.

It says each deployable owns its database/schema and secrets, with authenticated versioned contracts, stable identities, idempotency, durable outbox/inbox, no shared DB, no cross-service SQL, and no implicit distributed transaction. It explicitly characterizes current in-process/shared-store operation as compatibility mode, not independent deployment.

### Governance D-01 — approval-highwater projection constraint

`docs/rust-part3-governance-interface-contracts.md` states:

- D-01 remains limited to its approved approval-highwater transaction database; it is not a shared-database exception for three deployables.
- ADR 0003 continues to require separate Control, Execution and Governance database ownership and versioned cross-part contracts.
- Current in-process Store adapters place workflow, trust/reviewer, Governance decision/receipt/nonce and checkpoint state in one physical workflow SQLite file. Part 3 explicitly identifies this as a compatibility implementation that does not satisfy ADR 0003.
- The selected target keeps the minimum D-01 authorization projection in the Control-owned database, while Governance retains canonical authority and publishes authenticated versioned updates. Governance must not directly open or write the Control database.

The same document warns that the production provisioning runbook's separate `workflow.db` and `agg-trust-configuration.db` files are not authorized to be redirected/copied/migrated until a complete projection writer inventory, independent logical DB identity/generation/restore epoch, writer barrier/fencing, bounded busy policy, WAL/locking readback, schema/row digests, crash/restore/clone tests, rollback and external monotonic anchor are proven.

The architecture direction is now selected, but implementation gates remain:

1. Governance and Control owners must define and ratify the exact signed projection/receipt contract, including freshness, revocation races, nonce/replay, and UNKNOWN reconciliation.
2. All part owners must prove writer inventory, additive export/import, database identity/generation, cutover fencing, rollback and cross-process acceptance before the current combined compatibility Store is decomposed.

ADR 0003 lists the decision owner as **Project owner / maintainers**. The current Google Chat coordination request asks Governance and Execution owners to identify their concrete contract owners and return decisions, but no mapping/reply has been verified in this assessment.

## Safe migration choices for the decision owner

Option A is not selected. The project owner selected Option B; its remaining contracts and migration gates are specified below.

### Option A — retain D-01 as an explicit, time-bounded compatibility exception

- Keep one physical DB for the approval/trust projection that requires same-transaction reads.
- Continue to separate crate APIs and service authorities in-process; do not advertise independent DB ownership or independent rollback.
- Define a global host-level D-01 writer quiescence/fencing protocol before migration, restore, checkpoint transitions or production activation. The current Control `control.lock` is not that global barrier.
- Amend ADR 0003 or add a superseding decision naming the D-01 exception, its owner, expiry/review gate and evidence required to remove it.

This option preserves today's combined Store transaction topology but conflicts with the latest Part 3 contract and ADR 0003's per-deployable database ownership. It is rejected as the target architecture. The existing combined Store may remain only as a non-production compatibility implementation during migration planning.

### Option B — replace shared SQL with versioned Governance attestations and a defined consistency protocol

This is the selected direction for the three-database target. It requires owner-approved contracts before implementation. At minimum the contract must define:

1. **Authority and identity:** Governance alone owns canonical trust-root/reviewer state, monotonic per-domain versions, revocations, nonce consumption and receipt signing. Control never writes Governance tables or trusts caller-supplied trust identity.
2. **Control-owned projection:** define exact tables/events and inbox semantics for the minimum signed authorization/high-water projection needed inside Control's approval transaction. The projection is not Governance's source of truth and must carry source service identity, logical database identity/generation, version, digest, issued/expiry bounds and receipt lineage.
3. **Immutable evidence:** signed, domain-separated snapshot/decision envelopes bind exact trust-domain version, configuration fingerprint, provider, reviewer identity/version/status, candidate/workflow/plan digest, decision ID, nonce or nonce-consumption receipt, issued/expiry time and audience.
4. **Freshness and revocation:** specify whether every approval needs a synchronous Governance freshness check, a short-lived authorization lease, a globally fenced trust epoch, or bounded staleness. A locally replicated high-water alone cannot detect an unobserved new revocation. Missing, stale, expired, gapped, conflicting or unavailable Governance evidence must remain denied/unresolved.
5. **Ordering:** specify how a revocation races a decision already issued but not yet consumed by Control. State whether the Governance receipt is final, revocable before Control acknowledgement, or protected by a fencing generation/authorization lease. A simple signed snapshot is insufficient to claim same-instant revocation semantics.
6. **Nonce and replay ownership:** Governance must atomically consume checker/maker nonces and persist the decision/receipt/idempotency key in its own database. Control's inbox must persist the exact receipt and Workflow transition in one Control transaction. Exact retries must return the same receipt/decision; conflicting payloads or receipt reuse must fail closed.
7. **Cross-part lifecycle:** define a durable outbox/inbox state machine for Governance decision delivery, Control receipt acceptance, workflow approval/admission, timeout/unknown outcomes, reconciliation and crash recovery. Do not represent a partially completed saga as one ACID transaction.
8. **Migration boundary:** provision new empty target databases, export exact versioned rows/events with source logical DB identity, generation and restore epoch, verify schema/row digests and event chains, import idempotently, then fence old writers and perform a monotonic cutover. Define rollback compatibility and how external facts written after the snapshot are reconciled; never restore a stale snapshot as if it erased provider/process effects.

Until these details are approved, Option B is the selected architecture direction but not an implemented contract. It must not be approximated by adding an HTTP call inside `TrustApprovalVerifier`: doing so would introduce network I/O into the current SQLite approval transaction and still would not define the revocation race or crash-recovery boundary. Fetch Governance evidence before the Control transaction, then validate and consume the exact signed/versioned projection inside the Control transaction.
