## 1. Projection rules

The v2 implementation must publish two different, versioned logical projections:

- `anti_replay_state_sha256`: consumed one-use evidence, nonce uniqueness, policy high-water and related replay/revocation state.
- `execution_authorization_state_sha256`: the complete durable decision context actually consumed by approval, candidate reconstruction, immutable-plan validation, preparation, reviewer eligibility, dispatch and execution authorization. This includes the anti-replay inputs and relevant non-AGG workflow state.

This inventory does not define canonical SQL queries, final column normalization, schema-version numbers, or digest serialization. Those are V2-07/V2-08 deliverables. Stable ordering below is the observed current query ordering, not yet a frozen protocol.

### Anti-replay open items

- Complete every caller of approval/reviewer/knowledge verifier routines and identify any other durable nonce, idempotency, revocation or high-water store.
- Confirm all historical event schema versions and whether legacy approval events without signed evidence remain in the scan set (current approval code explicitly tolerates historic non-AGG events without the signed evidence envelope).
- Define event allowlist/version enforcement so a new security event cannot silently be omitted from the projection.
- Define how event payload raw bytes are parsed under the v2 strict raw-UTF-8/JCS boundary; current approval and reviewer paths include `JSON.parse()`/`JSON.stringify()` checks and are not a substitute for v2 strict parsing.

## 6. `approvals.raw_text` disposition

**Current disposition: the `approvals.raw_text` column is excluded as an authorization input.** Evidence:

1. It is declared in the `approvals` table and written by `WorkflowStore.approve()` (`src/runtime/job-store.js:213-217,6958-6959`).
2. `getLatestApproval()` materializes the full row, but `isApprovalCurrent()` only consumes `decision` and `proposal_hash` (`job-store.js:1297-1305`).
3. The active workflow readback calls `getJobTrace()` but explicitly returns only `approval_id`, `decision`, `actor`, `proposal_hash` and `created_at` (`server/index-v1.0.9-rc.71-versioned-approval-subsystem-20261030.js:2321-2336`).
4. Repository search of active `src/runtime` and the active RC.71 server found no `raw_text`/`rawText` predicate or field consumer; historical server snapshots are not active readers. `getLatestApproval()` and `getJobTrace()` use `SELECT *`, so they materialize the column internally, but current authorization consumes only decision/proposal hash and the public `getWorkflow()` readback strips it.

**Important distinction:** `WorkflowStore.approve()` also copies the same user text into the generic `approval.approved` event payload as `rawText` and uses it in the event dedupe key (`src/runtime/job-store.js:6965-6968`). The current reader inventory shows authorization/replay consumers use `proposalHash` and `approvalBinding`, not `rawText`; V2-08 should therefore omit `rawText` from the semantic payload projection while retaining the immutable `event_id` row identity. Because `event_id` itself is derived from `hash(rawText|proposalHash)`, this retains an incidental commitment to the text. Any future change to that event-ID derivation requires a projection-version change and a migration decision.

This exclusion is valid only while those conditions remain true. If `raw_text` becomes an authorization predicate, immutable binding input or user-visible approval readback field, the execution-authorization projection manifest must be revised and versioned.

## 9. Immediate implementation implications

- Do not implement V2-08 from this v0.1 document as if it were complete.
- Do not hash the physical SQLite database, WAL or SHM files.
- Do not treat the current append-only SQLite triggers as independent monotonic protection.
- The current two-database layout is a confirmed V2-05 migration requirement.
- Every writer listed above, plus any newly discovered writer, must be routed through one future durable transition gate and anchor lifecycle before its mutation can become executable.
- Unknown/unmapped reader or writer means projection is incomplete and authorization must fail closed.
