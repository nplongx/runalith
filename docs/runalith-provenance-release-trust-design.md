# Runalith provenance and independent release trust design

**Status:** design plus local Phase A verifier wired into read-only rollout preflight, strict hostile-object canonicalization, hosted builder/verifier workflow source, immutable trusted Plan Graph draft and approval/dispatch transaction guards implemented; production release remains BLOCKED and the hosted workflows have not yet been run to produce real attestations
**Prepared:** 2026-10-27
**Scope:** MCPB source-to-artifact provenance, independent release authorization, host verification, Goal/Idea Graph → Plan Graph → Execution Graph evidence, and safe rollback.

## 1. Decision summary

Runalith should adopt a small, fail-closed release chain built around:

1. An immutable source snapshot and a build receipt generated by a controlled builder.
2. An in-toto Statement carrying SLSA build provenance whose subject is the exact MCPB SHA-256.
3. Signature/identity verification by the host against administrator-provisioned builder roots and expected repository/build parameters. Cosign/Sigstore is a viable implementation where its identity and transparency guarantees match the deployment; it is not a substitute for release authorization.
4. A separately authorized release approval bound to the candidate digest, provenance digest, policy version, test evidence, installed baseline, and rollback digest.
5. A host-owned, signed checkpoint tied to an independently protected monotonic store, preventing replay, rollback, and trust-state substitution.
6. A pre-install consumer/host gate that verifies all evidence against its own trust policy before any installation or dispatch action.

Do **not** make a new signing key, test fixture, local hash, source-alignment report, passing test suite, or self-issued approval sufficient for production. These can be useful evidence but cannot establish the identity or authority of the system that produced them.

## 2. Evidence currently observed in the repository

The following are repository/test observations, not production authorization:

- The source-alignment tooling can compare archive entry bytes to a source snapshot and reports dirty Git state. A byte match does not prove who built the artifact or that a trusted builder emitted the report.
- `scripts/lib/external-trust-checkpoint-contract.mjs` verifies a signed checkpoint response and its sequence/digest fields. Its return value explicitly says continuity-source and key-provisioning authentication are not established by this function; those must be independently provided by the host.
- `scripts/validate-agg-trust-config.mjs` can validate a supplied verifier/reviewer configuration pair and reject shared providers or overlapping roots. It cannot make a user-supplied file administrator-owned by itself.
- The production trust runbook requires authority/key custody and separated trust domains. The active runtime must actually load the provisioned configuration for that runbook to count as operational evidence.
- The latest documented read-only rollout preflight remains **BLOCKED**. Its seven blockers are listed in §8. Historical Phase 2 archives do not match one exact reachable Git tree and must not be relabelled as source-matched artifacts.
- The latest documented Goal/Plan evidence checks found a proposal with nine Plan Graph steps lacking supporting evidence, unverified source verification, and no Execution Graph proposal. A structurally valid graph or `contract_ready` state alone is not evidence-ready or dispatch-authorized.

These findings are a snapshot of the work recorded in the integration dossier, not a claim that the live environment has been rechecked during every future use of this document. Re-run the read-only diagnostics before making a release decision.

## 3. Threat model and trust boundaries

Protect against accidental or malicious source/artifact substitution, dirty or untracked build inputs, a compromised package mirror, a candidate asserting its own trust, replayed or expired approvals, trust-root substitution, rollback to an incompatible build, stale/frozen trust metadata, and execution based on missing Plan-step evidence.

The following authorities must remain separate in policy and key custody:

| Authority | May assert | Must not be allowed to self-assert |
| --- | --- | --- |
| Source control/change authority | Repository, commit/tree, reviewed change state | Builder identity or production release approval |
| Build service | Source inputs, build definition, dependencies, output digest, build identity | Release approval or host trust roots |
| Test/evidence service | Results and reports bound to exact candidate digest | Builder identity or release authority |
| Release reviewer/authority | Approval for a specific candidate under a specific policy | Verifier roots or host monotonic checkpoint |
| Host/security administrator | Effective verifier/reviewer roots, revocation policy, checkpoint adapter and storage | Candidate source/build facts that have not been independently checked |
| Runtime/owner/provider | Authoritative workflow attempt, task, result, artifact and completion records | Missing plan evidence, approval, or source provenance |

Compromise of a trusted builder or host administrator remains a high-impact residual risk. Use protected build infrastructure, least privilege, auditable changes, key rotation/revocation, and independent review; do not imply that a signature alone solves insider compromise.

## 4. Proposed end-to-end evidence chain

```text
Reviewed source revision + clean source snapshot
        │ source tree digest, commit, submodules/dependencies, dirty-state policy
        ▼
Controlled builder ── emits MCPB + signed SLSA provenance attestation
        │               subject.digest.sha256 = exact MCPB digest
        ▼
Independent candidate verifier
        │ verify signer/builder identity, source repo, buildType, parameters,
        │ source snapshot digest, archive entries, manifest, tools, tests
        ▼
Evidence bundle ── tests, SBOM/dependency record if applicable, alignment report
        │ every report identifies exact candidate SHA-256 and tool/policy versions
        ▼
Independent release authority ── signed approval bound to candidate + evidence
        ▼
Host preflight ── effective trust configs + revocation + external monotonic checkpoint
        │ compare current installed baseline and independently verified rollback artifact
        ▼
Owner-authorized workflow drain/reconciliation; verify Plan-step evidence
        ▼
Explicit install/activation approval → runtime digest check → post-install verification
```

The arrow chain is conjunctive: a later stage cannot compensate for missing evidence in an earlier stage. A local JSON report is not an attestation unless its producer, subject digest, signature/identity, and policy are verified.

## 5. Evidence contract

Use the in-toto Statement v1 envelope/statement model and SLSA provenance predicate where practical. A release bundle should contain at least:

| Evidence | Required bindings | Authoritative producer |
| --- | --- | --- |
| Source snapshot record | canonical repository URI, immutable commit, tree digest, snapshot digest, submodules, tracked diff and full worktree status, clean/dirty decision | controlled source/export process |
| Build provenance | exact MCPB SHA-256 and size; builder identity; buildType; invocation parameters; source materials; dependency/material digests; toolchain; build start/finish | controlled builder, signed by platform identity |
| Candidate verification report | exact MCPB SHA-256; archive-entry inventory; manifest/runtime tool parity; source alignment; policy/tool versions; test command/result/exit code | independent verifier/test runner |
| Release approval | candidate digest; provenance digest; evidence-bundle digest; policy version; target environment; installed baseline digest/version; rollback digest/version; approver identity; expiry; unique nonce | release authority separate from builder and verifier |
| Host trust-state checkpoint | authority ID; sequence and previous digest; ledger and trust-domain digests; candidate and rollback digests; freshness; signed response to nonce | host-managed adapter + independently protected monotonic ledger |
| Runtime receipt | installed artifact digest; host generation/version; activation timestamp; post-install checks; approval/checkpoint references | host/runtime observer, not the candidate process |

Canonicalization must be specified once per signed object. Verify exact artifact digest before parsing package claims. Reject unknown security-critical fields, duplicate keys, malformed encodings, non-canonical timestamps, expired statements, unexpected repositories/build types/parameters, missing materials, and digest mismatches. Do not invent a new generic signing format if an established in-toto/SLSA envelope is adequate; define a versioned Runalith predicate only for fields those schemas do not represent.

Every evidence item must be content-addressed and immutable once referenced. Reports may refer to each other by digest, forming a DAG. The release approval must pin the root evidence-bundle digest, not merely filenames or mutable URLs.

## 6. Roles for the standards

- **SLSA provenance:** records where, how, and from which inputs the artifact was built. Start with hosted, signed provenance (SLSA Build L2-style guarantees) and assess whether the chosen builder can credibly satisfy hardened-build requirements before claiming L3. The host must check builder identity and expected provenance fields; the presence of a provenance document is not sufficient.
- **in-toto Attestation:** provides a standard statement/subject/predicate model to bind claims to an immutable artifact digest and to define typed attestations. Prefer existing predicate types before creating a Runalith-specific one.
- **Sigstore/Cosign:** can sign/verify the MCPB blob and its attestations with identity and transparency evidence. Pin the expected OIDC issuer and certificate identity (or a separately provisioned public key) in host policy. A valid signature from an unapproved identity is a rejection, not a warning.
- **TUF concepts:** use delegated roles, threshold approval where appropriate, metadata versioning/expiry, and protections against rollback/freeze/fast-forward attacks for release metadata. TUF is not automatically required as a full updater framework if Runalith's distribution model does not need it; the same security properties must still be implemented and tested.
- **Existing Runalith checkpoint contract:** retain the challenge nonce, candidate/rollback digest binding, sequence continuity, previous-checkpoint digest and strict freshness checks. Close the remaining trust gap by provisioning and attesting the adapter and monotonic storage outside the candidate/plugin trust domain.

## 7. Host verification policy

The host is the final policy enforcement point and must load trust configuration from an administrator-controlled canonical path or equivalent protected configuration service. The candidate must not be able to replace trust roots, approval policy, checkpoint adapter, or the monotonic store it is being checked against.

Before any install or dispatch, the host should:

1. Hash the candidate bytes and compare them to the requested digest and every signed subject binding.
2. Verify provenance signature and transparency evidence, expected builder identity, repository, source revision/tree/snapshot digest, build type, invocation parameters and material digests.
3. Verify the independent candidate-verification report and all required tests, with the exact candidate digest and exit statuses bound into the evidence bundle.
4. Verify the release approval's signer, role, scope, policy version, nonce, expiry, revocation status, candidate/evidence/baseline/rollback bindings.
5. Verify the host-signed checkpoint response against a host-provisioned key, then validate sequence/previous-digest continuity against an independently authenticated monotonic store. A local file or caller-supplied `continuity` object is not an authenticated store.
6. Compare the candidate and rollback to the exact installed baseline. Refuse version-only equivalence; require byte digests and file/entry parity, compatibility declaration, and a rollback exercise in an isolated environment.
7. Confirm workflow drain/reconciliation and required Plan Graph evidence from authoritative owner/provider/runtime records. Do not mutate or dispatch as a side effect of a diagnostic.
8. Emit a signed preflight decision that names each gate, its evidence digests, policy version and explicit PASS/BLOCKED reasons. A PASS is only for the evaluated digest and snapshot; any changed input invalidates it.
9. Re-hash the artifact immediately before installation, verify installed generation bytes afterward, and emit a host-owned runtime receipt. Fail closed on TOCTOU changes.

No code in the candidate itself should be able to set `productionAuthorityEstablished=true` merely because it can verify a signature. Authority depends on who provisioned the root, how the host adapter was authenticated, and whether the checkpoint state is independently protected.

## 9. Historical archives and mixed source lineage

Preserve the archive bytes, SHA-256 values, entry counts, README history, and frozen 71-path contract exactly. Current diagnosis classifies the eight historical archives as mixed/unattributed lineage because none matches one reachable Git tree; this does not prove ZIP corruption, nor does it identify an authenticated builder or exact source snapshot.

Resolution procedure:

1. Preserve each archive and existing report as read-only forensic evidence; do not rewrite archive contents or refresh a hash to make a check pass.
2. Search authoritative build logs, CI artifacts, source snapshots, object storage, and signed release records for the exact archive digest.
3. Reconstruct candidate source inputs only where a trusted source snapshot or build receipt actually exists. Compare all package entry bytes and dependency/toolchain inputs.
4. If exact lineage cannot be established, classify the archive `UNATTRIBUTED` and exclude it from release eligibility. Do not retroactively sign it and imply that the signature proves historical provenance.
5. Create a new candidate from a clean, reviewed, immutable source snapshot using the controlled builder and current frozen inventory rules. This is a new artifact and requires the full test, provenance, approval, host-preflight and rollback gates.

The 71-path contract is a gate, not an optimization target. If the legitimate new package has a different inventory, obtain an explicit reviewed contract change in a separate change process; never weaken the existing assertion inside the candidate-inventory test to force success.

## 10. Rollback and rollout protocol

Rollback is an independently authorized release operation, not merely selecting a lower semantic version. Before rollout, record the exact installed archive and installed generation digest, manifest/version, entrypoint digest, archive file inventory, configuration/schema expectations and state compatibility. The rollback candidate must have authenticated provenance and authority and must be compatible with the state produced by the candidate being rolled back.

Required sequence:

1. Validate rollback artifact and its compatibility against the actual installed baseline in an isolated environment.
2. Obtain independent release authorization binding both candidate and rollback digests.
3. Verify host trust configuration and external monotonic checkpoint.
4. Prove active jobs/tasks are drained or individually resolved by their owners; no blanket destructive cleanup.
5. Run all tests and source-to-bundle alignment against the exact candidate digest.
6. Re-run read-only preflight. Any missing or stale evidence remains BLOCKED.
7. After a separate explicit operator authorization, install through the host-owned lifecycle path, verify installed bytes, then collect post-install runtime evidence.
8. If post-install checks fail, follow the pre-authorized rollback plan only after revalidating the rollback digest, compatibility, and authority against the current state.

Never use the preserved RC.8 v18 artifact as rollback for installed RC.11 while its documented parity exceptions and version mismatch remain unresolved.

## 11. Implementation plan

### Phase A — evidence schema and policy (no production changes)

**Implemented subset (2026-10-27):** `scripts/lib/runalith-release-trust-contract.mjs`, `scripts/verify-release-evidence.mjs`, `tests/test-runalith-release-trust-contract.mjs`, and `docs/runalith-release-evidence-verifier.md` now define and test a strict local DSSE/in-toto/SLSA profile, distinct Ed25519 builder/verifier/release-authority roles, candidate/report/approval digest bindings, clean source snapshot requirements, required test evidence, nonce and expiry checks, and exact rollback-to-baseline digest/version matching. The verifier deliberately returns production `BLOCKED` even when every local cryptographic evidence gate passes; supplied policy roots and baseline observations are not authenticated by this tool. This is not the controlled hosted builder, Sigstore transparency verification, host-owned monotonic checkpoint, or runtime/install implementation described in later phases.

**Additional verifier hardening (2026-10-27):** the release-evidence contract's canonical JSON routine now inspects own property descriptors without evaluating getters and rejects accessors/setters, non-enumerable properties, sparse/decorated arrays, symbols, forbidden `__proto__` keys, non-plain objects, non-finite numbers, cycles and repeated object identities. Both policy validation and evidence verification validate an inert strict-JSON copy instead of reading caller-controlled policy properties. Regression tests verify a hostile policy getter is never invoked and malformed arrays fail closed. This is local contract hardening only; it does not authenticate the policy's administrator or establish production authority.

The current AGG graph path additionally freezes the authenticated Plan Graph draft tree and binds its identity-map entry to the exact draft hash, upstream snapshot/attestation/evidence manifest, and expiry; the Execution Graph consumer refuses caller-supplied source-verification metadata which differs from that authenticated draft. `WorkflowStore.approve()` and `WorkflowStore.dispatch()` now require host-runtime guards for AGG action-intent proposals and run those guards inside the SQLite `BEGIN IMMEDIATE` transition transaction. The guards revalidate the source snapshot, reviewer identity, candidate digest and immutable plan immediately before approval/dispatch; standalone stores without the host verifier fail closed. Isolated E2E covers an upstream snapshot mutation between approval and dispatch and confirms that no task is created.

The hosted pipeline source is now in `.github/workflows/runalith-provenance-builder.yml` and `.github/workflows/runalith-provenance-verifier.yml`, backed by `scripts/lib/hosted-builder-attestation.mjs` and `scripts/verify-hosted-builder-provenance.mjs`. The builder splits its low-privilege build/test job from an attestation-only job that does not execute candidate bytes; the independent workflow consumes the exact run artifact and runs `gh attestation verify` against the pinned repository/workflow/workflow digest/OIDC issuer/source commit/SLSA predicate. `docs/runalith-hosted-builder-pipeline.md` records the operator process and evidence boundary. These workflow files have passed local YAML parsing and their injected-output contract tests, but have **not** run on GitHub in this session; no real SLSA attestation, workflow identity or independent CI receipt is claimed as obtained.

- Define versioned source-snapshot, candidate-verification, release-approval and runtime-receipt schemas. Reuse in-toto/SLSA formats for provenance and standard signature envelopes.
- Define a machine-readable host policy: expected repository, builder identities, build types, approved parameters, required test set, candidate inventory policy, release reviewer role, validity periods and revocation rules.
- Add schema/contract tests for unknown critical fields, duplicate JSON keys, digest mismatch, wrong subject, wrong repository, dirty/untracked input, expired/replayed approval, nonce mismatch and policy-version drift.

### Phase B — controlled build and independent verification

### Phase C — host trust and anti-rollback

**Implementation status:** the local checkpoint contract verifies signatures, freshness, release binding and chain continuity, then requires one `commitCheckpointTransition` compare-and-swap to consume the challenge and advance sequence/high-water/previous-digest state atomically. A legacy nonce-only callback cannot satisfy this boundary. `scripts/lib/sqlite-external-checkpoint-transition.mjs` now supplies a transaction-based adapter contract that deliberately does not create or seed its schema/anchor; tests exercise it using two independent connections and a reopen boundary. This demonstrates local SQLite transaction behavior, not independent custody or production authority. The repository still lacks host-owned provisioning proof, authenticated adapter deployment and an independently protected monotonic store. Do not substitute a local SQLite file, hosted CI attestation or a JSON continuity object for those host authorities.

- Host/security administrators provision versioned verifier and reviewer configurations, separate providers and disjoint SPKI roots, rotation/revocation procedures, and key custody records.
- Provision the checkpoint adapter and monotonic store outside the plugin/candidate process; attest effective runtime configuration and external store identity.
- Extend rollout preflight to consume only authenticated evidence objects and emit stable per-gate findings. Tests must demonstrate that local JSON, test keys, self-issued approvals, fake continuity objects and replayed checkpoints cannot produce PASS.

### Phase D — runtime evidence and controlled rollout

**Implementation status:** source snapshot/evidence/Plan Graph candidate/reviewer/approval/dispatch revalidation is integrated in code, including the writer-lock guards described above. Production runtime receipt, active host's effective trust provisioning, live task drain proof and a baseline-compatible rollback exercise remain unverified. Existing rollout preflight must remain BLOCKED.

- Add owner-authorized reconciliation proof for active jobs/tasks; retain unresolved records on hold.

## 12. Acceptance criteria

**PASS** only when all of the following are true for the same candidate digest and current policy version:

- Source snapshot is immutable and independently reconstructable; no unrecorded tracked or untracked inputs are accepted.
- Signed provenance is valid and its builder identity, repository, build type, parameters and materials meet host policy.
- Every required test and inventory check passes with recorded exit status and exact candidate digest; frozen contracts remain intact.
- Release approval is independently authenticated, unexpired, unrevoked, nonce-bound, and pins candidate, evidence root, installed baseline and rollback digests.
- Host-owned trust configuration is effective, independently administered, and verifier/reviewer trust domains are separated.
- External checkpoint is freshly signed and validated against an authenticated monotonic high-water store with no gap, replay or rollback.
- Candidate and rollback are byte-identified and compatible with the actual installed baseline; rollback exercise passes.
- Active jobs and running tasks are drained or individually resolved with authoritative evidence.
- Every Plan Graph step has valid, content-addressed evidence; source and snapshot attestations are authenticated; Execution Graph/dispatch gates are independently verified.
- Post-install host receipt confirms installed bytes and runtime identity.

**BLOCKED** if any required evidence is missing, generated by an untrusted identity, stale, revoked, digest-mismatched, not bound to the same candidate, or only asserted by the candidate. A passing unit test, ZIP integrity check, byte-alignment report, local test key, approval label, or older version cannot override a failed gate.

## 14. Source-alignment provenance completeness (2026-10-27)

The source-to-bundle verifier's `buildInputs` must include not only files copied into the MCPB, but also every release-critical policy, verifier, workflow, rollout implementation, test contract and operator document that determines whether that candidate may be accepted. A change to those inputs must alter the content snapshot even if archive payload bytes remain unchanged. The report must separately expose exact archive-entry byte identity, source Git state, source provenance digest and release eligibility; these are distinct claims. It must recheck that the reported bundle path still contains the exact bytes captured before archive inspection.

The current implementation and tests bind the release-trust policy/verifier, hosted builder/verifier/signer workflows, rollout code, relevant regression tests and provisioning/design documentation. It hashes tracked diff and full Git porcelain status without publishing local paths. A dirty worktree can still byte-align, but its result is `DIRTY_GIT_TREE_BYTES_MATCHED_NO_AUTHENTICATED_BUILD_RECEIPT` and release eligibility remains blocked. The Execution Graph proposal verifier also rejects non-enumerable/accessor fields, cycles, repeated object identities, and non-JSON values; the builder detaches internally assembled proposals into a JSON tree before exposing them, so internal shared immutable contract objects cannot leak aliasing into the serialized proposal. A new source snapshot or alignment report never substitutes for authenticated hosted builder attestation, independent verification, release approval, host-effective trust configuration, protected external monotonic checkpoint, compatible rollback, or authoritative workflow drain proof.

## 13. Validation matrix

| Area | Positive case | Required negative cases |
| --- | --- | --- |
| Source/build provenance | Clean snapshot → signed provenance → exact archive digest | Dirty/untracked tree, wrong commit/tree, substituted archive, unknown builder, unexpected build parameter |
| Attestation/signature | Approved identity, valid signature and subject | Invalid signature, wrong issuer/identity, missing transparency proof where required, subject digest mismatch |
| Release approval | Independent reviewer approves pinned evidence root | Candidate self-approval, shared builder/reviewer authority, expired/revoked approval, nonce replay, policy drift |
| Checkpoint | Exact next sequence anchored in external store | Local-only continuity, stale response, replay, sequence gap, wrong previous digest, wrong candidate/rollback digest, altered trust roots |
| Candidate inventory | Frozen inventory passes exactly | Historical archive mismatch, path traversal, missing/extra entries, altered contract or refreshed historical hash |
| Workflow evidence | Owner-confirmed terminal outcome and linked artifacts | Missing lease, stale `status`, running task, truncated inventory, missing Plan-step evidence, absent Execution Graph proposal |
| Rollback | Independently approved artifact tested against actual baseline | Older-but-incompatible version, entrypoint mismatch, archive extras/missing files, state/schema incompatibility |
| Runtime | Host receipt matches installed generation digest | TOCTOU swap, installed-byte mismatch, stale runtime receipt, unapproved activation/dispatch |

Run unit/contract tests first, then isolated end-to-end tests with test-only keys, then read-only host preflight. Test-only roots must be impossible to load in production. Never call a test PASS a production trust proof.
