# Goal/Idea Graph and active-workflow reconciliation

This companion documents the read-only integrity overlay added to the reconciliation CLI. It supplements the versioned AGG architecture document without rewriting its benchmark-pinned historical bytes.

The same report includes `adaptiveGoalGraph`, a read-only integrity overlay for the persisted Goal/Idea Graph, Plan Graph/Execution Graph proposal event records, and planner telemetry. It validates stored revision identity/history, canonical content/evidence hashes, membership and edge provenance, edge identity/semantics, typed endpoints and recovery-edge contracts, including the recovery evidence references' membership in declared evidence nodes. Its table inventory is bounded (10,000 nodes, 50,000 revisions/memberships, 20,000 edges and 5,000 attestations); any clipped graph inventory leaves the snapshot hash unavailable and marks integrity as `INCOMPLETE_INVENTORY` instead of silently hashing a partial graph. For each observed goal it reconstructs the canonical snapshot representation and recomputes `snapshotHash`; this is compared with stored attestation bindings to identify stale snapshots. `attestations[].identityValid` means only the durable row and canonical payload bind together, and `snapshotFresh` means only the stored hash matches the reconstructed snapshot. The diagnostic intentionally does **not** attempt Ed25519 signature verification, trust-root ownership, independent-provider verification or claim adjudication; `signatureVerification` remains `not_attempted_requires_host_owned_trust_configuration`, and `planningAuthority` is always `NOT_ESTABLISHED_BY_READ_ONLY_DIAGNOSTICS`. A structurally clean graph, current hash binding or durable attestation row is not planning authority.

Planner telemetry diagnostics inspect the bounded latest 500 runs, compare each recorded knowledge-revision/provenance/evidence-reference identity with durable revisions/edges where available, classify run snapshot bindings as missing/current/unavailable/superseded, and re-resolve `runtime_resolver` artifact references against current artifact bytes, producer role contract, `artifact.created` event, exact successful result, attempt and completion event. Repository-local `file:` references are resolved only within the canonical source checkout, using the reference's own pinned SHA-256; no arbitrary external filesystem path is followed. The report marks recorded `lineage_verified`/`claim_verified` flags as self-reported telemetry, not authority. It explicitly does not adjudicate claim truth or independence. If source files change later (including docs), a historical content-addressed reference can become stale; preserve the old evidence/hash as historical and generate a new observation rather than rewriting old telemetry.

Persisted proposal events are inspected at `job.proposal_requested` (the proposals are nested JSON payloads, not separate rows in a dedicated AGG proposal table). The report recomputes a Plan Graph proposal fingerprint against its stored source/workspace/draft/binding/projection fields and checks Execution Graph wrapper/source/hash bindings. These are tamper-detection checks on current event bytes only; they are not provider signatures, trusted attestation, current-approval checks, immutable-plan pinning or dispatch authorization. Current workflow records may predate newer candidate event formats; absent records are an absence in this bounded store observation, not proof that no proposal ever existed elsewhere.

Treat diagnostics as a time-bounded observation. The report may include a bounded inventory of the latest 500 planner runs; if `plannerSummary.reportingTruncated` is true, collect a narrower run/goal analysis before drawing conclusions. Output paths must be new and unique. Do not put reports containing operational identifiers into a commit, public issue, or release artifact without an approved data-minimization review.

The current workflow schema does not persist an authoritative owner ID or provider ID. `conversation_key`, worker ID, run/session IDs and `/proc` observations are correlation hints, not authenticated owner/provider identity. PID observation includes process start ticks but remains `identityVerified:false` unless a persisted execution identity can be matched; do not infer process identity from PID or command hash alone. The task report now cross-checks task versus latest-attempt provider run IDs, active lease job/task and attempt bindings, presence of lease `owner_epoch`, and the runtime attempt versus the active task attempt. These are consistency checks only: a matching ID/epoch is not authenticated provider identity, and a missing epoch is a fencing-evidence gap rather than permission to recover. A report with missing or truncated lineage is unresolved, not evidence of absence. Verify owner/provider/runtime through host-owned records, re-query all IDs and event lineage, establish the true outcome, then use the documented owner-authorized lifecycle path and rerun diagnostics.

Job/task lifecycle flags are also emitted as structured `findings[]` entries. Each finding contains a deterministic content-derived `findingId`, stable `code`, `severity: BLOCKER`, `status: UNRESOLVED`, `gate: HOLD`, source subsystem/table names, relevant observed record IDs, a bounded evidence summary, an explicit remediation step and `authorizationGranted: false`. The ID is a reproducibility key for diagnostic content, not an authenticated signature, independent record, immutable ledger anchor or approval. Finding closure requires a fresh authoritative observation and the owner-authorized process; neither the finding ID nor the proposed remediation authorizes a transition.

## Operator procedure: one record at a time, diagnostic-only by default

The repository tools intentionally do not expose a `reset`, `retry`, `terminalize`, lease-release or dispatch operation for this report. A suggested recovery plan is a checklist, not an executable command. Use a fresh unique output path and narrow the query before contacting the record owner:

```sh
# Capture a new whole-active-set observation; the destination must not exist.
node scripts/reconcile-active-workflows.mjs \
  --db "$HOME/.chat-on-steroids/agent-orchestrator/workflow.db" \
  --limit 200 --out /tmp/reconcile-active-$(date -u +%Y%m%dT%H%M%SZ).json

# After selecting one exact job ID from that report, take a separate narrow observation.
node scripts/reconcile-active-workflows.mjs \
  --db "$HOME/.chat-on-steroids/agent-orchestrator/workflow.db" \
  --job-id '<exact-job-id-from-report>' \
  --out /tmp/reconcile-job-<ticket-id>-<fresh-utc-suffix>.json
```

Expected output for a successful diagnostic is JSON with `readOnly: true`, `authorizationGranted: false` on every recovery-plan item, explicit unresolved findings and a content hash for the report. A path collision, symlink/non-canonical path, unsupported schema or truncated inventory is a failed/incomplete observation; preserve the error and resolve it before any decision. Do not reuse a prior report as current state.

Before proposing a lifecycle transition, an authorized workflow owner and provider/runtime operator must jointly confirm, from host/provider-owned records: (1) the exact job/task and immutable plan identity; (2) the current process/runtime and provider execution identity, not merely a PID or `conversation_key`; (3) the active attempt and lease fencing/owner epoch, including any provider-side lease not represented in SQLite; (4) event → attempt → result → artifact → completion ordering and content hashes; (5) whether a dispatch intent was consumed or an external side effect may already have happened; and (6) the approved transition for the observed outcome. If any item is unavailable or conflicts with the report, leave the record unchanged and escalate to its owner.

Record the owner's decision and source evidence in the existing authorized operational/audit system, not by editing this JSON report. If the approved system offers a dry-run, run it against the exact job/task/attempt and capture its decision before execution. Use its documented idempotency key and concurrency/fencing preconditions; do not reuse the diagnostic `idempotencyKey` as authorization or as an external command token. Execute only through that owner-authorized lifecycle interface, then immediately collect a fresh single-record report and verify the event/result/artifact/lease state against the approved outcome. If a result is ambiguous, the provider is unavailable, the attempt changed, the lease/owner epoch differs, or a post-action verification fails, stop—do not automatically retry or compensate. Preserve the before/after report hashes and owner decision reference in restricted audit storage.

No safe local recovery command exists for the currently reported `EXECUTING` jobs/running tasks because authoritative owner/provider/runtime evidence and lifecycle authority have not been supplied. A missing lease remains a blocker, not a recovery trigger.

The separate `scripts/reconcile-active-workflows-v2.mjs` diagnostic now explicitly reconciles task hierarchy references as well as job/event/result lineage. For each observed task it validates that `parent_task_id` resolves inside the same job. `dependency_json` contains **workflow-plan task IDs**, not durable `tasks.task_id` values; the diagnostic resolves these through the job's immutable `workflow_plans.plan_json` and each materialized task's `metadata_json.workflow_plan_task_id`. In addition to checking plan hash/job/workflow identity, unknown plan IDs, absent or ambiguous materialization, incomplete prerequisites and plan dependency cycles, it compares each task's observed `dependency_json` set against the declared dependency set for that exact immutable plan task. Missing or substituted edges produce `TASK_DEPENDENCY_MATERIALIZATION_MISMATCH` with expected, observed, missing and unexpected plan-task IDs. This detects both omitted dependencies and extra dependencies even when every referenced ID exists in the plan. These are diagnostic blockers (`TASK_PARENT_*`, `TASK_DEPENDENCY_*`) only; they never alter task rows or authorize retries/terminalization. `lifecycleEvidence.taskHierarchy.completeness` remains diagnostic-only. Event lineage status is now unambiguous: `ALL_REFERENCES_RESOLVED` means all *observed references* match durable records; `NO_REFERENCES_OBSERVED` means no reference was found and explicitly does not prove complete lineage; `CONFLICTING` means one or more observed references cannot be resolved. None of these statuses authenticates owner/provider identity.

Plan-to-Execution Graph proposal creation also validates dependency ordering independently of caller-supplied draft hashes: every dependency must name a unique earlier Plan Graph step. Self-edges, forward references and cycles fail with `EXECUTION_GRAPH_DEPENDENCY_INVALID` before a proposal is returned. This is a structural correctness gate, not source attestation or execution authority; the proposal remains review-only and all approval/dispatch guards still revalidate current evidence.

Persisted Plan Graph proposal diagnostics now independently validate semantic cross-graph lineage, not just the proposal fingerprint: every step ID must be unique, each `sourceNodeId` must resolve to one unique actionable (`task` or `experiment`) node in the embedded Goal/Idea `source_graph`, and every dependency must resolve to a distinct earlier draft step. The diagnostic also checks that each `requires_all`/`depends_on` edge between mapped action nodes is reflected in the projected draft dependencies. Violations produce `AGG_PLAN_GRAPH_PROPOSAL_SOURCE_LINEAGE_INVALID` plus a bounded `sourceLineage.findings` list and force the proposal readiness assessment to `BLOCKED`. This catches a proposal whose hashes are internally consistent but whose steps were remapped to nonexistent or unrelated source nodes. It remains read-only and does not assert source signature validity, evidence truth, reviewer approval, or dispatch authority.

At the read-only observation recorded on 2026-10-26, the workflow database had 60 `EXECUTING` jobs, 61 `running` tasks and zero rows in `task_leases`. The same observed store had 15 knowledge nodes, 15 revisions, 15 memberships, 16 edges, two Goal/Idea scopes with no stored verification attestations, 56 planner runs and 373 evidence-reference rows. Of the latest bounded planner telemetry, 29 artifact-reference rows were rechecked against current durable lineage and one failed; six distinct repository-local file references no longer matched their recorded content hashes. The event inventory contained 136 proposal-request events, two Plan Graph proposal payloads, zero Execution Graph proposal payloads and zero candidate-created events. These figures are a historical observation—not a liveness judgment, completeness guarantee, or authorization. Some file-reference mismatches are expected after later source/docs changes; never revise the historical hash to make it appear valid. Re-run the command for a fresh record and reconcile each affected task with its responsible owner/provider. No lease row, missing PID, empty run/session ID, stale timestamp or absent completion event proves the worker dead. Require exact attempt/result/artifact/completion lineage and host/provider runtime evidence before considering an owner-authorized lifecycle transition. Until that per-record evidence exists, hold the jobs/tasks and keep the production rollout blocked.
