# AGG external anti-rollback checkpoint v2 research

**Date:** 2026-10-30  
**Status:** research memo; design review only. No runtime or production state changed.

## Executive summary

The v2 proposal correctly identifies the v1 verifier's central defect: it authenticates signed state-hash fields without comparing them with independently measured local state. The current v1 verifier accepts only `ledger_state_sha256` and `trust_domain_state_sha256` as signed values; it has no expected-local-digest inputs. The rollout runbook also records that the approval replay and policy high-water state lives in `workflow.db`, separate from the trust-configuration ledger. V1 therefore does not establish local-state equality or protect the complete approval security state.

Two proposed v2 mechanisms need redesign before implementation:

1. **One SQLite connection, one attached read transaction, or one SQL statement does not establish a documented cross-database point-in-time snapshot.** SQLite documents WAL snapshot isolation per database and explicitly says that multi-database transactions in WAL mode are atomic only per database file, not as a set. No SQLite documentation located defines a common snapshot timestamp across independently written attached databases. A single statement is consequently insufficient evidence for the claimed cross-database barrier.
2. **External CAS followed by local SQLite COMMIT is a distributed dual write.** If the external CAS commits and the process crashes or local COMMIT fails, remote high-water advances while local state remains old. Keeping `BEGIN IMMEDIATE` open during a network round trip blocks other workflow writers but cannot make the external store and SQLite commit atomically. A signed receipt cannot remove this failure window.

The safe direction is to make security-state changes recoverable state machines. Prefer consolidating the anchored security records into one SQLite database. If two databases remain, every writer must participate in one host-owned cross-database serialization barrier. For each change, persist a local pending intent, obtain a remote idempotent reservation, commit the local state as pending, then finalize the remote monotonic checkpoint. Execution stays blocked until a signed final receipt is durably recorded and independently revalidated. Recovery queries the authority by a stable operation ID and reconciles exact digests; it never guesses or retries with a fresh nonce while outcome is unknown.

Remote attestation must bind the fresh authority challenge and the exact state digest to evidence from a measured, policy-approved helper. A root-owned executable hash, process descriptor, path/inode check, or helper self-report alone does not prove that the helper ran in an uncompromised environment or that it measured the intended SQLite snapshot. The selected platform must define its measured boot/workload chain, attestation verifier, freshness, audience, data-binding, revocation and threat model.

Until these corrections, host/admin dependencies and failure tests are resolved, v2 must remain a blocked design proposal. Do not infer that v1 or a local SQLite callback proves production anti-rollback custody.

## 2. Verified platform and standards facts

### 2.1 SQLite snapshots, WAL and ATTACH

SQLite's WAL documentation says a reader sees a stable snapshot of a database as of the beginning of its read transaction. Commits by other connections remain invisible to that reader until its transaction ends. This is a per-database snapshot guarantee, not a promise that two independently written database files share one logical commit point ([SQLite Isolation](https://www.sqlite.org/isolation.html), “Isolation And Concurrency”, especially WAL snapshot isolation; [SQLite Database Snapshot API](https://sqlite.org/c3ref/snapshot.html), “Database Snapshot”).

`ATTACH DATABASE` adds another database file to a connection. SQLite documents multi-attached-database transaction atomicity only when the main database is not `:memory:` and journal mode is not WAL. Under WAL, transactions remain atomic within each individual database file; a crash during a multi-file COMMIT can leave some files committed and others not ([SQLite ATTACH](https://sqlite.org/lang_attach.html), §2; [SQLite WAL](https://sqlite.org/wal.html), §1 “Overview”).

This atomicity rule concerns writes, but it also defeats the proposed inference that “one attached transaction” supplies a general cross-file consistency primitive. SQLite documents the snapshot for each database file and does not specify a cross-file common snapshot time. Each file may have its own committed WAL frames and writer. Reading both through one connection/statement does not itself create an application-level barrier that all writers must obey. Treat cross-database snapshot atomicity as **unproven** unless a separate coordinator or single-database design supplies it.

WAL commits append commit records to `-wal`; the main database file can remain unchanged until checkpointing. The `-wal` and `-shm` files are part of WAL operation, and a read-only WAL database can be opened only when the required sidecar conditions are met (SQLite WAL, §§2 and 5). Hashing only the main file therefore omits committed logical state. Conversely, hashing raw `.db`, `-wal` or `-shm` bytes is not a stable logical-state digest: checkpointing and WAL lifecycle can alter physical bytes without changing SQL-visible state. Use SQLite queries against a pinned, coherent read view for logical projections; treat sidecar handling as a SQLite connection/backup concern, not as an ad hoc byte concatenation.

The SQLite Online Backup API can produce a consistent snapshot of a live database as of the start of the backup operation. It is a useful way to materialize each database independently, but it does not create a shared point-in-time snapshot across two database files; the cross-database barrier is still required before backing up both files ([SQLite Online Backup API](https://sqlite.org/backup.html), “The Online Backup API”).

`BEGIN IMMEDIATE` starts a write transaction immediately and blocks other writers to that database; in WAL mode it has the same writer-reservation role as `EXCLUSIVE` ([SQLite Isolation](https://www.sqlite.org/isolation.html), WAL concurrency discussion; [SQLite Transactions](https://www.sqlite.org/lang_transaction.html), transaction modes). It does not reserve writers to a different SQLite database, lock an external service, or make two independent commits atomic.

### 2.2 Canonical serialization and digests

RFC 8785 (June 2020) defines JSON Canonicalization Scheme (JCS) for repeatable hashing/signing bytes. It constrains input to I-JSON, prohibits duplicate object property names, requires Unicode strings, limits JSON numbers to IEEE-754 double representation, preserves string data without Unicode normalization, recursively sorts object keys using UTF-16 code-unit ordering, and fixes primitive serialization. JCS is an **Informational** RFC, not an Internet Standards Track specification ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html), §§1, 3.1–3.2 and 5).

The v1 `canonicalJson()` in `scripts/lib/external-trust-checkpoint-contract.mjs` sorts JavaScript object keys and uses `JSON.stringify()`, and its inert-object validator rejects non-finite numbers and unusual prototypes. It does not enforce all JCS/I-JSON constraints (for example, duplicate keys cannot be recovered after ordinary JSON parsing, and safe interoperable number range / lone-surrogate rules need explicit handling). The trust-configuration module has a simpler local canonicalizer. A v2 cross-component digest must specify one canonicalization profile and version, use a strict parser that rejects duplicate keys before materialization, reject unsupported numeric/string values, and share test vectors across producers and verifiers.

NIST FIPS 180-4 (published August 2015; NIST notes a revision is planned) specifies SHA-256 among the Secure Hash Standard algorithms and describes digests as a way to detect message changes ([NIST FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final), abstract and publication metadata). SHA-256 provides a 256-bit digest; it does not authenticate who computed it, establish truth of input data, prove freshness, or prevent rollback. Those properties require trusted measurement, signature verification and independently protected monotonic state.

### 2.3 Signatures and envelope structure

RFC 8032 (January 2017) specifies EdDSA, including Ed25519. Ed25519 public keys are 32 octets and signatures are 64 octets; verification checks canonical point/scalar decoding and the signature equation ([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.html), §§5.1.5–5.1.7 and §7.1). The current v1 verifier's 64-byte signature-length and canonical-base64 checks are sensible encoding checks, but v2 still needs a closed, versioned envelope with explicit algorithm, key identity, authority/store identity, audience, issued/expiry times, nonce, operation ID, previous sequence/digest, candidate/rollback binding, state projection version and measurement evidence binding.

Sign exactly defined canonical bytes. Define whether the signature covers the complete envelope excluding only the signature field; reject unknown/missing fields; bind a protocol-specific context/domain separator; pin keys by canonical SPKI fingerprint; enforce validity and revocation; and keep checkpoint-authority and store-attestation keys independently administered. A signature proves that the holder of a configured key signed those bytes. It does not prove the underlying state was measured correctly or that the key is controlled independently.

### 2.4 CAS, replay and ambiguous outcomes

HTTP semantics explain why idempotent requests can be retried after a lost response: repeating the same intended request has the same effect. A client should not automatically retry non-idempotent operations without a way to know the original was not applied ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), §9.2.2). HTTP conditional requests such as `If-Match` are a standard model for applying a state change only when the current representation matches an expected validator (RFC 9110, §13.1.1). These semantics are useful protocol patterns, but a bespoke external store must still define its durable atomic transaction and recovery API.

The current local SQLite callback atomically compares expected sequence/digest, rejects a used nonce, records the nonce and advances high-water in one local SQLite transaction. That is a good local CAS shape. It is not a distributed transaction with the workflow database. The v2 remote service must atomically persist: operation ID, request nonce, expected prior sequence/digest, exact new digest, candidate/rollback binding, and result receipt. The same operation ID/request bytes must return the same durable outcome on retry. A different payload under the same operation ID must be rejected. A read-only `GET operation-status(operation_id)` must return `NOT_FOUND`, `RESERVED`, `COMMITTED` or `ABORTED` with an authenticated record and receipt. Do not treat timeout as failure or success.

### 2.5 Host measurement and attestation

The RATS architecture separates the **Attester**, **Verifier** and **Relying Party** roles: an Attester produces Evidence, a Verifier appraises it against policy and produces an Attestation Result, and the Relying Party applies its own policy before relying on that result. It also describes an Attesting Environment that collects measurements from a Target Environment and notes that the bottom attesting layer is typically designed to be immutable or difficult to modify ([RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html), §§3.1, 4 and 7.4). RFC 9334's nonce-based freshness model requires an unpredictable nonce from the appraising entity to be included in signed Evidence or an Attestation Result; matching it establishes that the claims were signed after the nonce was generated, but does not by itself prove when the underlying claims were generated (§10.2). The EAT nonce claim requires at least 64 bits of entropy, and EAT use must provide a freshness mechanism ([RFC 9711](https://www.rfc-editor.org/rfc/rfc9711.html), §§4.1 and 9.3).

These standards establish the roles and freshness concepts, but they do **not** establish that this host has a TPM/TEE, that a generic Linux process can obtain trustworthy Evidence, or that platform boot measurements automatically prove the contents of a SQLite database. The verifier must trust the Attester's measurement layers and protect the attestation key; compromise of either the key or the Attesting Environment undermines the assurance ([RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html), §§3.1 and 12.1). A protocol that claims database-state measurement therefore needs an approved measured execution path that actually opens and projects the exact database state, plus explicit binding of the challenge, audience, projection version and digest into the Evidence.

## 3. Design gaps and corrections

### 3.1 The proposed ATTACH snapshot barrier is not established

The design's §3.5 preferred approach—one read-only connection with both files attached and one statement materializing both projections—overclaims SQLite guarantees. The two databases are WAL databases in the current deployment (`workflow.db` is explicitly configured WAL; trust-ledger journal mode is not explicitly set in its module). SQLite's WAL documentation expressly disclaims cross-file atomicity for attached databases. A single read statement is not a documented common-snapshot protocol, and no common writer serialization is imposed across the trust-ledger writer and WorkflowStore writer.

**Correction:** choose one of these explicit contracts:

1. **Preferred: consolidate all checkpointed security state into one SQLite database.** Put effective trust-config history, approval security events, approvals and the checkpoint projection under one SQLite file and one transaction/snapshot boundary. A schema migration and ownership plan are required.
2. **If split files remain: introduce a host-owned global writer barrier.** Every process and every code path that can write either file must acquire the same exclusive barrier before any relevant write and hold it through commit. Snapshot helper obtains the shared barrier, opens SQLite read transactions for both files, reads both projections, then releases it. The barrier must be enforced outside the plugin's voluntary call graph (for example, a host service or OS-level lock under root-owned policy). Any writer that bypasses it invalidates the guarantee. This gives application-level serialization; it is not a SQLite cross-file snapshot feature.
3. A versioned epoch/seqlock can be an alternative only if every writer atomically marks a write-in-progress and final epoch in an independently durable coordinator and readers prove the same stable even epoch before and after both reads. Specify crash recovery and fail closed on abandoned/ambiguous epochs. A process-local mutex or timestamp comparison is insufficient.

The design's descriptor/path pinning is necessary but incomplete. It must address the active SQLite connection's actual main-file and WAL handles, sidecar identity, symlink/path traversal, replacement between descriptor discovery and SQLite open, WAL reset/checkpoint while reading, and helper privilege/namespace boundaries. A pre/post inode comparison does not prove that the SQLite connection read from the already-inspected descriptor. Prefer a host helper with a defined descriptor-passing/openat strategy and integration tests for replacement races; otherwise report snapshot identity unverified.

### 3.2 Hash logical projections, not SQLite file bytes

The design is right to reject hashing only the main database file. It should be explicit that the target is a **logical state commitment** over a versioned projection, not a digest of database file bytes. WAL commits may be visible through SQLite while absent from the main file; checkpointing may fold WAL pages into the main file without changing SQL-visible state. Raw page bytes, freelist pages, page layout, vacuuming and checkpoint timing can change without an authorization-state change.

Define two separate workflow projections. Do not call the anti-replay projection a complete execution-authorization-state digest.

**Anti-replay-state digest.** This narrower component covers durable facts whose purpose is preventing reuse or rollback of one-use approval evidence and policy versions: every `approval.approved` event (complete canonical payload, event identity and row/order identity), maker/checker nonces embedded in signed evidence, every `adaptive_goal.approval_policy_version_observed` event and its nonce/version/hash/identity, reviewer-identity attestation and consumption/replay events, and any nonce/revocation ledger used by those verifiers. The current scans are visible at `src/runtime/adaptive-goal-approval-subsystem.js:307–369`. This digest answers: *can previously consumed approval or identity evidence, or an older policy version, be replayed?*

**Execution-authorization-state digest.** This broader component covers every durable input that can change the result of current approval, candidate reconstruction, immutable-plan validation, reviewer eligibility or dispatch. At minimum include:

- Include schema/contract version, relevant `sqlite_schema` table/index/trigger definitions, required PRAGMA values, and all rows that affect the authorization decision. Avoid hashing unstable physical artifacts such as autoindex names or page numbers unless deliberately part of the contract.
- Include all five effective trust domains, exact scope/provider/config version/fingerprint, every SPKI fingerprint and key ID, key validity/revocation metadata, and exact ledger history/event rows. Reject missing/duplicate domains and inconsistent effective config versus latest durable observation.
- Include the relevant `jobs` row and `workflow_runtime_state` row, including state/status, active task and phase/attempt fields used by lifecycle gates.
- Include the complete ordered proposal event history (`job.proposal_requested` and `job.proposal_refined`), because `getCurrentProposal()` selects the latest by `created_at,rowid`; include event ID, type, payload and ordering identity, not only current proposal hash.
- Include all `approvals` rows and fields used by latest-row selection (`approval_id`, `job_id`, `decision`, `actor`, `proposal_hash`, `created_at`, stable identity/order). `isApprovalCurrent()` selects latest by `created_at DESC,rowid DESC` and compares its decision/hash with the current proposal (`src/runtime/job-store.js:1282–1310`).
- Include `workflow_plans` row and exact canonical plan JSON/hash/metadata, its unique `workflow.plan_compiled` event, and every policy attachment/snapshot used to validate the plan (`src/runtime/job-store.js:1146–1182`).
- Include the AGG candidate event (`adaptive_goal.execution_plan_candidate_created`) with complete canonical payload, fingerprint, reviewed action intents, candidate hash and event identity.
- Include source Plan Graph / Execution Graph proposal snapshots and source bindings; source goal/idea graph snapshot hash and verifier attestation; task bindings; source evidence and lineage records.
- Include all `tasks`, `attempts`, `results`, active/inactivated `artifacts`, relevant workflow events and referenced session/lineage rows consulted by candidate readiness, reviewer artifact validation, dispatch and task preparation. `getJobTrace()` currently reads several of these families (`src/runtime/job-store.js:8623–8639`); server candidate reconstruction traverses source graph/evidence (`server/index-v1.0.9-rc.71-versioned-approval-subsystem-20261030.js:6488–6614, 6618–6715`).
- Include custom workflow definitions, role-profile versions/bindings, validation-profile content hashes, workspace write scopes, required operations and policy pack snapshots when those inputs participate in `compileExecutionPlan()` (`src/runtime/job-store.js:1184–1214`).
- Include all anti-replay-state inputs above, plus reviewer identity evidence, sandbox action claim/completion/failure ledger or execution lease/fencing state consulted by the actual dispatch/action path.
- Define whether raw `approvals.raw_text` is excluded as non-security content. If excluded, prove no authorization/readback path depends on it. Avoid returning row payloads in reports; compute in the helper and emit only digest, schema/projection version, bounded counts and safe diagnostics.
- Reject malformed, duplicate-key, noncanonical or unknown authorization event payloads. A versioned event allowlist is useful only if every new authorization/replay/revocation/identity event is forced through a code review and schema-version gate before it can affect authorization.

The anti-replay-state digest and execution-authorization-state digest answer different questions. The former detects rollback/reuse of consumed approval evidence and policy high-water. The latter detects changes to the full current decision context: job, proposal, approval, plan, candidate, policy/role bindings and evidence lineage. The aggregate checkpoint must bind both. A valid anti-replay digest alone cannot prove that the current job, proposal, plan, candidate, evidence or runtime state remains the one approved for dispatch.

The design's current `approval_security_state_sha256` name is ambiguous. Replace it with two explicit v2 fields (for example `anti_replay_state_sha256` and `execution_authorization_state_sha256`) or formally define that it is the broader execution-authorization digest and add a separate anti-replay digest. Do not leave the field name implying completeness while its projection contains only approval/replay rows.

The proposal currently includes candidate-created events and all approval rows. That makes **every append or mutation in those sets a checkpoint-relevant state transition**. Define which writers must obtain a new external anchor and how the system behaves between ordinary candidate creation and approval. If those records are intentionally outside the checkpoint lifecycle, narrow the projection and prove their rollback is caught by a separately anchored immutable binding.

### 3.3 JCS profile and envelope must be normative

The current canonicalizers are similar in spirit but are not a complete cross-language canonicalization contract. Select RFC 8785 JCS or another precisely specified deterministic binary encoding; do not use a repository-private “sort keys + JSON.stringify” variant without complete rules and cross-language test vectors. Reject duplicate JSON keys during parsing, lone surrogates, non-I-JSON values and numbers outside interoperable constraints. Encode 64-bit sequence/version values as bounded integers with a defined range or decimal strings; never permit a JavaScript precision-loss path.

Use domain-separated component envelopes, for example `agg-trust-domain-state/v2`, `agg-trust-ledger-state/v2`, `agg-anti-replay-state/v2`, and `agg-execution-authorization-state/v2`, then an aggregate `agg-external-checkpoint-state/v2` containing schema ID and component digests. Hash canonical UTF-8 bytes with SHA-256. Record canonicalization profile/version and projection code identity in the measured evidence. A component digest must not be reusable as a digest in another protocol context.

### 3.4 Remote challenge cannot authenticate a caller-supplied digest

The proposal says the challenge contains locally measured digests, then says the authority must not sign arbitrary plugin-supplied hashes. Those statements need a protocol ordering and trust boundary. If the plugin sends a digest in an ordinary request and the remote authority echoes/signs it, the signature authenticates the authority's response, not the truth of the digest. If the host helper signs a digest with a software key that the plugin can invoke with arbitrary bytes, that alone does not prove the helper computed the digest from the exact live DB state.

Define two linked exchanges:

1. The independent authority issues a fresh challenge containing authority/store IDs, one-time nonce, audience, expiry, expected prior sequence/digest and operation ID. The challenge is authenticated and durably reserved at the authority.
2. A measured host attester opens the exact database handles under the approved snapshot barrier, computes the projection itself, and produces attestation evidence that binds the challenge nonce, audience, operation ID, database identities, projection/helper measurement and resulting digests. The verifier checks the quote and policy. The authority then accepts only that verified evidence and uses its digest as the CAS candidate.

If the post-write state is being attested, a separate helper process cannot read uncommitted workflow rows on its own SQLite connection under normal isolation. The proposal's “compute from that transaction” requires either trusted in-process code using the writer connection to produce the projection, or a protocol that first persists a pending intent and then attests the resulting committed/pending state. A helper must not accept a caller-provided digest as the measured source of truth. Do not claim hardware attestation of a digest unless the measured code, data path and nonce/data binding actually establish that claim.

### 3.5 Remote CAS before local COMMIT is unsafe

The proposed sequence stages workflow writes under `BEGIN IMMEDIATE`, computes the staged digest, requests remote CAS, receives a commit receipt, then commits local SQLite. Failure after remote CAS but before local COMMIT produces a remote checkpoint for a state that does not exist locally. SQLite's transaction guarantees cannot roll back the remote service. Conversely, local commit before remote CAS can leave an unanchored local state if the remote service is unavailable. This is a classic distributed transaction boundary.

Holding a SQLite writer lock across network I/O is also operationally hazardous: `BEGIN IMMEDIATE` serializes workflow writers; slow/unavailable remote calls increase lock duration and contention. It does not lock the separate trust ledger. The currently installed guard already runs while WorkflowStore's approval writer transaction is open, so inserting a remote network call into that callback would extend this critical section.

The local pending-intent transaction must also be durable across the failure model the protocol claims to survive. SQLite documents that in WAL mode `synchronous=NORMAL` can lose a recently committed transaction after power loss or a hard reset, whereas `synchronous=FULL` syncs the WAL on each commit and provides ACID durability in WAL mode ([SQLite PRAGMA synchronous](https://sqlite.org/pragma.html#pragma_synchronous); [SQLite WAL](https://sqlite.org/wal.html), §2.3). `WorkflowStore` explicitly enables WAL but does not explicitly pin `PRAGMA synchronous` in its connection setup (`src/runtime/job-store.js:128–139`). The v2 implementation must choose and verify a durability setting consistent with its power-loss threat model; it must not call a pending intent durable merely because the SQL `COMMIT` returned.

**Correction:** make the external service support a non-authorizing prepare/reservation and idempotent finalize, then make local state explicitly pending until finalization. A receipt-first single-step CAS cannot guarantee atomicity across SQLite and a remote store.

## 4. Recommended safe protocol

The following protocol is a proposal for security-owner review. It deliberately gives up availability during ambiguity; execution must remain blocked until reconciliation succeeds.

### 4.1 Read-only observation / checkpoint verification

1. Load a host-root-owned policy pinning the exact snapshot helper, projection contract, verifier roots, allowed platform measurements, external authority/store IDs, endpoint/audience, validity/revocation policy and independent administration requirements.
2. Acquire the global snapshot barrier (or read from the consolidated single DB). Resolve exact DB and WAL handles with no-follow/path-component checks. Reject deleted/replaced/ambiguous descriptors, unexpected sidecars, unexpected journal modes, unknown schema or helper mismatch.
3. Start SQLite read transactions on all relevant DBs while the barrier is held. Read the full versioned projections through SQLite so committed WAL state is included. Verify stable identity and barrier generation before/after. Keep the barrier through the final read and digest computation.
4. Canonicalize with the single specified JCS profile, compute SHA-256 component digests and aggregate digest. Fail closed on any malformed, unknown or inconsistent row. Return only digest/version/count metadata.
5. Obtain a fresh authority challenge. Produce host attestation binding challenge nonce, audience, operation ID, exact projection digests, DB identities and helper measurement. The independent verifier validates platform evidence, helper identity, policy and freshness. The authority signs an observation containing exact challenge and digest fields plus current sequence/digest.
6. The local verifier compares every signed digest byte-for-byte with independently measured digests and checks authority/store identity, key validity/revocation, challenge, expiry, candidate/rollback binding, expected previous digest and sequence. A valid signature over a mismatch is a rejection.

### 4.2 Security-state transition with recoverable external commit

1. **Prepare locally.** Under the normal workflow `BEGIN IMMEDIATE`, validate all current trust roots, policy, maker/checker quorum, replay state and immutable candidate. Generate a stable `operation_id` and challenge nonce. Insert a durable pending transition intent containing expected prior sequence/digest, operation ID, exact target bindings and intended projection version. Do not make approval/dispatch executable. Commit this small local intent transaction. Do not hold a workflow writer lock across a remote request.
2. **Reserve remotely.** Submit the operation ID, nonce, expected previous sequence/digest, candidate/rollback binding and intended change descriptor to the external authority. The remote store atomically reserves this operation/nonce with an expiry and returns a signed `PREPARED` receipt. It does not yet advance the public high-water. Exact retry returns the same prepared result; same ID with different request bytes is rejected.
3. **Apply locally as pending.** Re-enter `BEGIN IMMEDIATE`; verify pending intent still matches, revalidate trust/policy and replay invariants, stage exact approval/high-water rows plus operation ID and `ANCHOR_PENDING` status, compute the logical projection from this same transaction connection, and commit. The execution/dispatch guard must reject all pending states. If local commit fails, query the remote operation and abort/expire the reservation; never assume it was not applied without querying.
4. **Attest and finalize remotely.** The trusted host attester computes the committed projection under the cross-DB barrier and binds the exact resulting digest to the prepared operation ID/nonce and attestation evidence. The external authority verifies evidence and performs one durable CAS from expected prior high-water to the new digest. It atomically records nonce consumption, operation outcome and signed `COMMITTED` receipt. Exact retry is idempotent and returns the same receipt.
5. **Finalize locally.** Verify receipt signature, operation ID, nonce, prior and new sequence/digest, candidate/rollback and component digests. Under `BEGIN IMMEDIATE`, mark the pending transition `ANCHORED` and store the receipt digest/reference (or full receipt if safe); read back exact values; commit. Dispatch is allowed only after this state is `ANCHORED` and a fresh read-only external continuity check succeeds.
6. **Recover ambiguity and local rollback.** If any response is lost or timeout occurs after reserve/finalize, query the authority read-only by the same operation ID. `COMMITTED` must return the exact same receipt; verify it and complete local finalization. `PREPARED` may be resumed or explicitly aborted under policy. `NOT_FOUND` is actionable only when the service guarantees durable query semantics and operation retention. A local restore can roll `workflow.db` back to a point before the pending-intent row existed, thereby erasing the local operation ID; querying only by an ID recovered from the local database would then miss the orphaned remote reservation. The authority must therefore also expose the current anchored head and all outstanding operations/reservations scoped to the external store identity, with authenticated pagination or an equivalent complete reconciliation contract. On startup and before any new transition, compare the local anchored state with that remote head and reconcile every remote outstanding operation; any unknown reservation, missing local intent, digest/sequence mismatch or incomplete listing keeps approval and dispatch quarantined. Conflicting digest/sequence, expired reservation, missing receipt or unknown status keeps the transition quarantined. Never issue a new nonce or start a second transition until the prior operation set is resolved.
7. **Trust-configuration changes use the same lifecycle.** A new/revoked trust root changes effective trust-domain and trust-ledger projections. Its effective configuration must remain non-executable until the exact resulting state is anchored. Specify how emergency revocation is fail-closed when the external authority is unavailable.

This is a recoverable saga, not a claim of cross-system atomic commit. Its invariant is that no local state is executable until remote finalization is proven and locally recorded. The authority must support reservations/operation status and durable idempotent outcomes. If it cannot, use an owner-operated maintenance window with a protocol that can safely quarantine and manually reconcile all partial states; do not use the proposed receipt-before-local-commit sequence as if it were atomic.

## 5. Implementation and test implications

Before code changes, security owners should approve the projection schema, snapshot mechanism, external API state machine, attestation profile and availability behavior. Then implement and test these requirements:

- **SQLite snapshot correctness:** concurrent writes to both DBs while snapshotting; commits between first read and second DB read; WAL append/checkpoint/reset; long readers; busy/locked errors; read-only WAL sidecar permissions; database/WAL replacement and symlink races; helper crash; barrier bypass; writer process crash while holding/abandoning the barrier. Prove every writer participates. Verify `SNAPSHOT_NOT_ATOMIC` blocks approval/dispatch.
- **Logical-state digest:** same SQL-visible state before/after checkpoint yields same digest; committed WAL-only rows are included; checkpointing and VACUUM do not change digest; any security-relevant row/field/schema/trigger change changes digest or fails closed; missing/duplicate trust domains; provider/SPKI collisions; key validity/revocation changes; duplicate JSON keys; noncanonical payloads; unknown security event types; stable tie ordering; malformed payloads.
- **Canonicalization and crypto:** RFC 8785 test vectors including UTF-16 property ordering, escaping, numbers and Unicode edge cases; cross-language producer/verifier vectors; digest domain separation; altered field/unknown key/missing field rejection; Ed25519 RFC 8032 vectors; malformed/noncanonical base64/signature; wrong key, revoked key, wrong audience/context, stale/future timestamps and wrong authority/store ID.
- **Raw JSON boundary:** send duplicate member names and escaped duplicate aliases (for example `"nonce"` plus `"\\u006eonce"`) through the actual adapter stdout parser and prove rejection before object materialization; test invalid UTF-8, BOM, trailing JSON, excessive nesting/bytes/nodes and unsafe integer tokens. Also test the exported verifier with an already parsed object and document that duplicate-key detection is impossible at that API boundary; every production caller must use `parseStrictJson()` on raw bytes first. For persisted approval/reviewer event payloads, test the current `JSON.parse()` plus exact `JSON.stringify()` round-trip check and consider using `parseStrictJson()` consistently.
- **Projection completeness:** mutate each anti-replay input independently and prove anti-replay-state digest changes; separately mutate job state/status, active task/runtime phase, proposal history/order, approval decision/actor/hash/order, workflow plan JSON/hash/compiled event, policy attachment, candidate event, role/custom workflow/validation profile, source graph/knowledge snapshot, task/attempt/result/artifact and reviewer-attestation evidence. Prove execution-authorization-state digest changes or verification fails closed. Include equal-timestamp rows to exercise current `rowid` tie-breaks. Demonstrate that unchanged anti-replay digest with changed job/plan/evidence is still rejected by the execution-authorization-state digest.
- **Attestation:** nonce replay and expiry; nonce/digest/audience/operation-ID binding; altered digest after quote; wrong helper measurement/version; helper not root-owned or replaced; stale boot measurement; wrong PCR/TEE policy; untrusted verifier; compromised-but-valid application process; host administrator with ability to replace DB and helper; compromised local OS/root; network MITM; helper invocation with caller-supplied digest. Document what each platform can and cannot attest.
- **External CAS:** concurrent CAS; stale prior digest; sequence rollback/gap; nonce reuse; same operation ID/same bytes returns same receipt; same operation ID/different bytes rejects; crash after reservation; crash after local pending commit; crash after remote finalize but before local finalize; timeout before/after remote commit; read-only operation-status reconciliation; receipt replay; authority failover and durable replication. Prove a local workflow transaction is never executable while remote status is unresolved.
- **Approval integration:** approval rows and `approval.approved` event are one staged local change; policy high-water event is included; one-use maker/checker nonces remain unique; approval retry returns original evidence; dispatch rechecks anchor state under its writer boundary; all candidate/approval/trust writers that alter projected state trigger the anchoring lifecycle. Add explicit pending/anchored state to the low-level `WorkflowStore` guard so handler preflight cannot bypass it.
- **Backup/restore and custody:** restore old `workflow.db`, old trust DB, both DBs and sidecars together, remove triggers/schema, replace DB while helper is active, restore remote service backup, fail over to stale replica, and replay old signed receipt. The external authority's monotonic high-water and operation ledger must survive its own restore/failover. A separate administrator must verify this property.

Do not run `--advance-external-checkpoint` in these tests or diagnostics. Use disposable databases and a fake authority only for protocol-state-machine tests; fake keys and local stores cannot satisfy production authority.

## 6. Owner/admin decisions required

1. **Security owner:** approve exact component projection schemas, event allowlist governance, canonicalization profile, digest versioning, what state transitions require a checkpoint, and whether candidate/approval records are all anchored at creation time.
2. **Host/platform administrator:** choose single-database consolidation or provision the global writer barrier; specify how every process is forced to participate, how exact SQLite/WAL handles are pinned, and who owns helper deployment/upgrade/revocation.
3. **Attestation/platform owner:** identify actual TPM/TEE/remote-attestation platform, measured boot and workload claims, helper measurement chain, verifier and policy, nonce/audience/data-binding profile, revocation path, and explicit assumptions about root compromise and malicious host administrators.
4. **External checkpoint authority/operator:** specify a durable monotonic store, independent control plane, operation-ID idempotency, prepare/reserve/finalize/abort/query semantics, retention and disaster recovery, replica consistency, CAS linearization point, nonce lifetime and exact signed receipt schema. State whether the service can return the same receipt after a lost response.
5. **Trust administrators:** define independent authority/key custody, SPKI pin rotation/revocation, separation between checkpoint signer and store attester, and emergency revocation when the external store is unreachable.
6. **Workflow owner:** decide whether approval must be blocked while the external anchor is unavailable, how pending approvals are presented/recovered, and whether existing approval rows/events can be migrated without changing semantics.
7. **Operations owner:** define bootstrap ceremony, out-of-band first checkpoint, break-glass procedure, recovery authorization and evidence retention. The application must not self-bootstrap trust-on-first-use.
