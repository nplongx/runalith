# Runalith hosted builder and independent verifier

**Status:** workflow implementation is in the repository; it has **not** been run on GitHub in this work session. No GitHub SLSA attestation or verifier receipt is claimed to exist until the corresponding workflow runs and its evidence is downloaded and checked.

## Flow and trust boundaries

Three workflows deliberately separate build execution, independent verification, and verifier-attestation signing:

1. [`.github/workflows/runalith-provenance-builder.yml`](../.github/workflows/runalith-provenance-builder.yml) is manually dispatched from a protected `main` ref. Its `build-and-test` job has `contents: read` only and no OIDC/attestation permissions. It checks out the exact `github.sha`, runs `npm ci`, `npm test`, docs/site/package-reproducibility checks, builds the MCPB to an exclusive runner-temporary path, inspects ZIP integrity, records exact SHA-256 and source-to-bundle alignment, and runs `scripts/test-mcpb-candidate.mjs` against extracted runtime bytes. It uploads the candidate and the evidence generated by that job.
2. `attest-exact-build` is a separate job. It does not checkout repository source, install dependencies, unzip or execute candidate code. It treats the prior job's artifact as opaque bytes, re-hashes the candidate and validates the associated source-alignment contract, then calls the pinned `actions/attest` action to create the GitHub/Sigstore SLSA provenance attestation for those exact candidate bytes.
3. [`.github/workflows/runalith-provenance-verifier.yml`](../.github/workflows/runalith-provenance-verifier.yml) runs on `workflow_run` only after a successful builder run on the canonical repository's `main` branch. It checks out verifier code from the default branch, downloads the specific source run's evidence bundle, checks artifact/checksum/alignment binding and invokes `scripts/verify-hosted-builder-provenance.mjs`. That CLI calls `gh attestation verify` with the exact repository, signer workflow, signer workflow digest, OIDC issuer, source digest/ref, SLSA predicate type and the hosted-runner-only constraint. It validates the verified statement's exact candidate SHA-256, SLSA source repository/ref/workflow/commit bindings, and the pinned platform `builder.id`. Freshness is based on the signed transparency-log/timestamp-authority timestamp exposed by the verifier—not an arbitrary timestamp copied from the predicate.
4. In that read-only verifier workflow, the exact source commit is checked out into a separate `source/` directory. It reruns `npm test`, hosted-contract tests, docs/site/package checks and candidate fast test; rebuilds the MCPB a second time and requires byte-for-byte equality; then recomputes source-to-bundle alignment. It constructs a strict candidate-verification predicate bound to the exact candidate SHA-256, source snapshot, policy version/digest, raw evidence-report digests, entry-inventory digest and fixed required-test set. The predicate is generated only after these independent checks have passed.
5. [`.github/workflows/runalith-verification-attestation-signer.yml`](../.github/workflows/runalith-verification-attestation-signer.yml) is a **third workflow with a separate OIDC identity**. It runs only after the independent verifier succeeds. Its signer job downloads evidence as opaque bytes, repeats API and offline Sigstore-bundle verification, validates evidence-DAG/policy/test/source/rebuild bindings, then signs `https://runalith.dev/attestations/hosted-candidate-verification/v1`. It does not checkout source, run npm, unzip packages or execute candidate code. Builder, verifier and verifier-attestation signer have separate workflow identities; none is the production release authority.

Action references are pinned to full commit SHAs in the workflow. The branch-protection/ruleset, workflow permissions, repository ownership and whether administrators may bypass rules are external GitHub settings and cannot be proven from the YAML file. Have the repository/security administrator inspect those settings before treating the workflow identity as an accepted production builder.

## Run instructions

After these changes have been reviewed and merged through the repository's actual protected branch process, an authorized maintainer may manually run **Runalith controlled provenance builder** from the `main` branch in GitHub Actions. It should refuse to start on an unprotected/non-main ref. The successful builder workflow will start the separate verifier workflow automatically through `workflow_run`.

Retrieve both workflow logs and the uniquely named artifacts:

- `runalith-build-<source-commit>` — test-only MCPB, SHA-256 file and source alignment report produced by the low-privilege build job.
- `runalith-provenance-<source-commit>` — the exact candidate bytes, same checksum/alignment records, and Sigstore attestation bundle created by the attestation-only job.
- `runalith-independent-verification-<source-commit>` — the independent verifier's report and the verified input evidence.
- `runalith-verified-candidate-<source-commit>` — candidate bytes, hosted policy, candidate-verification predicate and the Sigstore bundle that signs that predicate using the separate verifier-workflow identity.

Do not use these filenames alone as evidence. Download by the actual workflow run ID, verify each artifact digest, inspect the run conclusion and signer certificate/transparency evidence, and keep the source commit, candidate SHA-256, SLSA statement, alignment report and verification report together. The GitHub CLI verifier fetches the attestation associated with the exact repository via the GitHub API; do not replace this with trusting fields from a caller-authored JSON report or a bundle-only check if repository rename/current-ownership validation is required.

The CI build report intentionally keeps `releaseEligibility` blocked because source-to-bundle alignment and a successful test suite alone do not prove who provisioned the build identity or approve release. The hosted verifier's exit code 0 means only that the signed builder provenance was verified against the encoded policy. It does not mean the candidate is production eligible.

## What is still missing

- A separately provisioned, independently administered release-authority identity and an approval attestation bound to the exact candidate/evidence-bundle/policy digests, target environment, installed baseline/rollback digests, expiration and one-time host nonce. The hosted policy deliberately says `target_environment: not-for-production`; the verifier-attestation signer cannot issue this release approval.
- The effective host verifier and reviewer trust configs, their administrator/change custody, disjoint public roots, key rotation/revocation evidence and proof the active host process actually loaded those exact versions.
- A host-owned checkpoint adapter with an authenticated channel to an independently protected monotonic store; no adapter or service endpoint is present in this repository that can establish that host fact.
- A protected host preflight that consumes the independently verified outputs and revalidates the same source attestation, reviewer role, approval, baseline/rollback and workflow drain at the approval/dispatch/install state-transition boundary.
- An observed GitHub workflow run on the reviewed commit, external branch protection evidence, independently verified builder and verifier attestation bundles, and a tested non-production rollback. These are not fabricated by unit tests or a local build.

## Local regression tests

`node --test tests/test-hosted-builder-attestation.mjs tests/test-hosted-verification-predicate.mjs tests/test-runalith-hosted-workflows.mjs` tests policy/statement bindings and workflow boundaries. Fake `gh` output tests contract behavior only; it is not an actual GitHub attestation. `node --test tests/test-runalith-release-trust-contract.mjs` separately tests the local Ed25519 DSSE profile. Production stays BLOCKED until real external evidence satisfies every gate.

## Official references

- [GitHub `actions/attest`](https://github.com/actions/attest) — signed SLSA provenance and Sigstore bundle output.
- [GitHub CLI `gh attestation verify`](https://cli.github.com/manual/gh_attestation_verify) — repository/workflow identity, source digest, OIDC issuer, predicate and transparency timestamp verification. Its documentation explicitly warns that statement predicate fields are user-controllable; validate those fields against the host policy instead of trusting their presence.
- [GitHub `actions/download-artifact` releases](https://github.com/actions/download-artifact/releases) — pinned action revision used by the cross-workflow artifact consumer.
